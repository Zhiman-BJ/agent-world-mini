# Agent-World Mini 环境契约 v2.0

本文定义一个环境的数据声明 `environment.json` 及其物理状态目录。配套机器校验文件为
`schemas/environment.schema.json`。本文是字段语义和存储规则，JSON Schema 是基础结构
约束；两者同时满足才是合法环境。

`environment.json` 面向 Loader、ToolGen、Runtime 和 Validator。它声明数据怎样访问，不保存真实
记录和文件内容：结构化记录存入 SQLite，需要专业工具直接处理的文件存入 Filesystem Scope。

## 1. 完整示例

下面先给出一份完整声明。该环境包含两个 Record Set、一个关系，以及多个同构工程目录组成的
Filesystem Scope。

```json
{
  "schema_version": "2.0",
  "environment_id": "drawing_review_001",
  "name": "工程图纸审核环境",
  "description": "包含工程项目、图纸记录以及按项目组织的 DXF 文件，支持离线查询、校验和任务副本修改。",
  "record_sets": [
    {
      "record_set_id": "project",
      "name": "工程项目",
      "description": "一条记录表示一个工程项目及其文件目录入口。",
      "access": "read_only",
      "key_fields": ["project_id"],
      "fields": {
        "project_id": {
          "type": "string",
          "description": "工程项目的稳定标识。",
          "nullable": false
        },
        "project_name": {
          "type": "string",
          "description": "工程项目名称。",
          "nullable": false,
          "minLength": 1
        },
        "project_directory": {
          "type": "string",
          "description": "该项目在 drawing_projects Scope 中的相对目录。",
          "nullable": false,
          "reference": {
            "kind": "filesystem_path",
            "scope_id": "drawing_projects",
            "target": "directory"
          }
        }
      }
    },
    {
      "record_set_id": "drawing",
      "name": "工程图纸",
      "description": "一条记录表示一份图纸及其可查询元数据。",
      "access": "read_only",
      "key_fields": ["drawing_id"],
      "fields": {
        "drawing_id": {
          "type": "string",
          "description": "图纸的稳定标识。",
          "nullable": false
        },
        "project_id": {
          "type": "string",
          "description": "图纸所属工程项目的标识。",
          "nullable": false
        },
        "title": {
          "type": "string",
          "description": "从图框中读取的图纸标题。",
          "nullable": true
        },
        "drawing_path": {
          "type": "string",
          "description": "DXF 文件在 drawing_projects Scope 中的相对路径。",
          "nullable": false,
          "reference": {
            "kind": "filesystem_path",
            "scope_id": "drawing_projects",
            "target": "file"
          }
        }
      }
    }
  ],
  "relationships": [
    {
      "relationship_id": "drawing_to_project",
      "description": "每份图纸都属于一个存在的工程项目。",
      "from": {
        "record_set_id": "drawing",
        "fields": ["project_id"]
      },
      "to": {
        "record_set_id": "project",
        "fields": ["project_id"]
      },
      "cardinality": "many_to_one"
    }
  ],
  "filesystem_scopes": [
    {
      "scope_id": "drawing_projects",
      "name": "工程图纸项目目录",
      "description": "多个结构一致的工程项目；每个项目包含项目说明和一组可检查、可修改的 DXF 图纸。",
      "access": "copy_on_write",
      "structure": {
        "kind": "directory_collection",
        "path": "projects/*",
        "layout": [
          {
            "kind": "file",
            "path": "project.json",
            "description": "当前项目的说明文件。",
            "required": true,
            "format": "json",
            "content_validation": "strict"
          },
          {
            "kind": "directory",
            "path": "drawings",
            "description": "当前项目的图纸目录。",
            "required": true,
            "layout": [
              {
                "kind": "file_collection",
                "path": "*.dxf",
                "description": "当前项目包含的 DXF 图纸。",
                "required": true,
                "format": "dxf",
                "content_validation": "strict"
              }
            ]
          }
        ]
      }
    }
  ]
}
```

对应物理存储：

```text
<environment_root>/
├── environment.json
├── state/
│   ├── records.sqlite
│   │   ├── table: project
│   │   └── table: drawing
│   └── filesystem_scopes/
│       └── drawing_projects/
│           └── projects/
│               ├── project_a/
│               │   ├── project.json
│               │   └── drawings/
│               │       ├── floor_01.dxf
│               │       └── floor_02.dxf
│               └── project_b/
│                   ├── project.json
│                   └── drawings/
│                       └── plan.dxf
```

对应记录中的路径值：

```text
project.project_directory = projects/project_a
drawing.drawing_path      = projects/project_a/drawings/floor_01.dxf
```

路径从 `drawing_projects/` 这个 Scope 根开始，不包含环境根目录，也不包含
`state/filesystem_scopes/drawing_projects/` 前缀。

## 2. 环境包与可见性

固定物理布局：

```text
<environment_root>/
├── environment.json
└── state/
│   ├── records.sqlite
│   └── filesystem_scopes/<scope_id>/
```

| 路径 | 内容 | 任务是否可用 |
| --- | --- | --- |
| `environment.json` | 数据结构和访问边界 | 是，由系统读取 |
| `state/records.sqlite` | 所有 Record Set 的基线表 | 是，只能经结构化工具访问 |
| `state/filesystem_scopes/<scope_id>/` | 文件工具可访问的基线材料 | 是，经对应 Scope 访问 |

存在性规则：

1. `record_sets` 非空时必须存在 `state/records.sqlite`；
2. 每个 `scope_id` 必须有同名的 `state/filesystem_scopes/<scope_id>/` 目录；
3. `record_sets` 和 `filesystem_scopes` 至少一项非空；
4. Loader 不向任务暴露数据库文件本身或未授权的其他 Scope；
5. 基线状态不在任务中原地修改，`copy_on_write` 数据先复制到任务隔离区。

`environment.json` 使用 UTF-8、标准 JSON，不允许注释、尾随逗号、重复键、`NaN` 或
`Infinity`。除 `fields`、`properties` 这种名称映射外，所有对象都是闭合对象，不能增加本契约未
定义的字段。

## 3. 顶层字段

顶层对象固定包含七个字段：

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `schema_version` | string | 是 | 固定为 `2.0` |
| `environment_id` | string | 是 | 环境的稳定全局 ID |
| `name` | string | 是 | 1 至 120 字符的显示名称 |
| `description` | string | 是 | 场景、数据范围和离线边界 |
| `record_sets` | array | 是 | 可按字段查询的记录集合，可为空 |
| `relationships` | array | 是 | Record Set 之间已验证的关系，可为空 |
| `filesystem_scopes` | array | 是 | 文件工具可访问的文件或目录范围，可为空 |

`description` 说明环境是什么，不写当前记录数或文件数。数量由程序从 `state` 计算，避免补充数据后
声明过期。

ID 规则：

| ID | 格式 | 唯一范围 | 同时用作 |
| --- | --- | --- | --- |
| `environment_id` | `^[a-z][a-z0-9_]{2,127}$` | 发布系统 | 环境目录标识 |
| `record_set_id` | `^[a-z][a-z0-9_]{1,62}$` | 当前环境 | SQLite 表名 |
| `relationship_id` | `^[a-z][a-z0-9_]{2,127}$` | 当前环境 | 关系标识 |
| `scope_id` | `^[a-z][a-z0-9_]{1,62}$` | 当前环境 | Scope 目录名 |

`record_set_id` 和 `scope_id` 不使用 `sqlite_` 前缀，也不使用 `raw`、`derived`、`output`、
`temp`、`misc` 等处理阶段名或兜底名。

## 4. Record Set

一个 Record Set 对应 `state/records.sqlite` 中一张同名表。

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `record_set_id` | string | 是 | 逻辑集合 ID 和 SQLite 表名 |
| `name` | string | 是 | 显示名称 |
| `description` | string | 是 | 首句必须说明“一条记录代表什么” |
| `access` | enum | 是 | `read_only` 或 `copy_on_write` |
| `key_fields` | string[] | 是 | 稳定组合键；没有可靠键时为 `[]` |
| `fields` | object | 是 | 字段名到 Field Definition 的映射，至少一项 |

### 4.1 `access`

| 值 | 运行时含义 |
| --- | --- |
| `read_only` | 工具只能读取基线记录 |
| `copy_on_write` | Runtime 建立任务副本后，工具可以修改副本 |

Agent 不直接访问 `records.sqlite`。`copy_on_write` 也不允许工具绕过结构化接口修改数据库文件。

### 4.2 `key_fields`

`key_fields` 中的字段共同唯一标识一条记录：

1. 字段必须存在于当前 `fields`；
2. 只能使用 `nullable=false` 的顶层标量字段；
3. 非空组合必须在表中唯一；
4. 复合键按数组顺序解释且不能重复字段；
5. 来源没有可靠业务键时使用 `[]`，不能随机伪造业务 ID；
6. 确定性生成的技术 ID 必须可复算；生成系统负责保存其生成依据。

### 4.3 `fields`

字段名匹配 `^[a-z][a-z0-9_]{0,62}$`，并与 SQLite 列名完全一致。每个顶层字段对应一列；
`object` 和 `array` 以规范 JSON 文本存入该列，由 Loader 解码。

## 5. Field Definition

每个字段定义至少包含：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `type` | enum | `string`、`integer`、`number`、`boolean`、`object` 或 `array` |
| `description` | string | 该值在当前 Record 中的准确业务含义 |
| `nullable` | boolean | 顶层表示是否允许 SQL `NULL`；嵌套位置表示是否允许 JSON `null` |

不同 `type` 允许的附加字段：

| `type` | 附加字段 |
| --- | --- |
| `string` | `format`、`pattern`、`minLength`、`maxLength`、`enum`、`const` |
| `integer` | `minimum`、`maximum`、`exclusiveMinimum`、`exclusiveMaximum`、`multipleOf`、`enum`、`const` |
| `number` | 与 `integer` 相同 |
| `boolean` | `const` |
| `object` | `properties`、`required`、`additionalProperties` |
| `array` | `items`、`minItems`、`maxItems`、`uniqueItems` |

`enum` 非空、无重复，成员类型与 `type` 一致。`enum` 和 `const` 不能同时出现。空字符串、空数组和
空对象不能代替 `null`。

### 5.1 Object

`object` 表示由当前记录拥有、不需要独立寻址的值对象：

```json
{
  "type": "object",
  "description": "图纸页面尺寸。",
  "nullable": true,
  "properties": {
    "width_mm": {
      "type": "number",
      "description": "页面宽度，单位为毫米。",
      "nullable": false,
      "exclusiveMinimum": 0
    },
    "height_mm": {
      "type": "number",
      "description": "页面高度，单位为毫米。",
      "nullable": false,
      "exclusiveMinimum": 0
    }
  },
  "required": ["width_mm", "height_mm"],
  "additionalProperties": false
}
```

`properties` 至少一项；`required` 可为空但不能重复；`additionalProperties` 必须为 `false`。
`required` 控制键是否出现，嵌套字段的 `nullable` 控制出现后的值能否为 `null`，二者相互独立。

### 5.2 Array

`array` 表示当前记录拥有的多值属性：

```json
{
  "type": "array",
  "description": "图纸的专业标签。",
  "nullable": false,
  "items": {
    "type": "string",
    "description": "一个专业标签。",
    "nullable": false,
    "minLength": 1
  },
  "uniqueItems": true
}
```

数组是否允许 `null` 由外层 `nullable` 决定；元素是否允许 `null` 由 `items.nullable` 决定。
需要独立查询、关联或更新的对象集合应拆为 Record Set，不能藏在数组中。

### 5.3 嵌套边界

Object 和 Array 的容器深度最多为 2。合法形态包括 `object -> array -> scalar` 和
`array -> object -> scalar`；深度 2 内不能继续增加 Object 或 Array。

嵌套字段不能进入 `key_fields`、不能作为 Relationship 端点、不能声明文件引用，也不能被其他
Record 单独引用。需要这些能力时应拆成独立 Record Set。

### 5.4 文件路径 `reference`

只有顶层 `string`，或 `items.type=string` 的顶层 `array`，可以声明：

```json
{
  "reference": {
    "kind": "filesystem_path",
    "scope_id": "drawing_projects",
    "target": "file"
  }
}
```

| 字段 | 值 |
| --- | --- |
| `kind` | 固定为 `filesystem_path` |
| `scope_id` | 必须引用当前环境中存在的 Scope |
| `target` | `file` 或 `directory` |

实际值是相对于该 Scope 根的 POSIX 路径。禁止绝对路径、URL、空路径、反斜杠以及 `.`、`..`
路径段。路径必须存在，解析后不能逃逸 Scope，并且实际类型符合 `target`。

多个 Record 可以引用同一路径；一条 Record 也可以用字符串数组引用多个路径。文件不需要单独建模
为 Record，也不需要强制分配 `file_id`。

## 6. Relationships

一条 Relationship 只包含：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `relationship_id` | string | 环境内唯一关系 ID |
| `description` | string | 可以根据两端字段判断真假的业务关系 |
| `from` | endpoint | 来源 Record Set 和字段 |
| `to` | endpoint | 目标 Record Set 和字段 |
| `cardinality` | enum | `many_to_one` 或 `one_to_one` |

Endpoint 固定包含 `record_set_id` 和非空 `fields`。端点只能引用顶层标量字段。

完整性规则：两端字段数量相同且类型兼容；`to.fields` 组合唯一且非空；所有非空来源组合必须命中
目标；复合来源要么整组为空，要么整组非空；`one_to_one` 还要求来源组合唯一。

一对多使用反向的 `many_to_one`。多对多增加关联 Record Set，再声明两条 `many_to_one`，不能用
ID 数组替代关系。

## 7. Filesystem Scope

Filesystem Scope 是文件工具的最小授权和复制边界。一个 Scope 对应且只对应：

```text
state/filesystem_scopes/<scope_id>/
```

即使只有一个文件，物理上仍有 Scope 目录；文件存放在该目录内部。Scope 之间不能通过路径或
符号链接共享文件。

### 7.1 Scope 字段

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `scope_id` | string | 是 | 逻辑范围 ID，同时是物理目录名 |
| `name` | string | 是 | 显示名称 |
| `description` | string | 是 | 材料内容、目录组织和文件工具用途 |
| `access` | enum | 是 | `read_only` 或 `copy_on_write` |
| `structure` | object | 是 | 工具可以依赖的稳定文件或目录结构 |

一个 Scope 内的材料应具有同一用途、访问模式和结构语义。不要把“所有下载文件”放进一个 Scope；
来源证据、README、网页快照等只有在任务工具确实需要读取时才进入 Scope。

### 7.2 Structure 节点通用语法

顶层 `structure` 必须有：

| 字段 | 适用节点 | 含义 |
| --- | --- | --- |
| `kind` | 全部 | `file`、`file_collection`、`directory`、`directory_collection` |
| `path` | 全部 | 相对当前节点根的确定路径或 glob |
| `format` | 文件节点 | 小写稳定格式名，不带点 |
| `content_validation` | 文件节点 | `strict` 或 `allow_invalid`；省略时为 `strict` |
| `layout` | 目录节点 | 非空的子节点数组 |

嵌套在 `layout` 中的节点还必须增加：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `description` | string | 该分支存放什么、供什么处理 |
| `required` | boolean | 在每一个父目录中是否必须存在或至少匹配一项 |

文件节点不能有 `layout`；目录节点不能有 `format` 或 `content_validation`。

### 7.3 `path` 的相对基准

路径按节点递归解析：

```text
顶层节点
└── path 相对于 state/filesystem_scopes/<scope_id>/

目录节点匹配到某个目录后
└── 其 layout 子节点的 path 相对于这个匹配目录

directory_collection 匹配到多个目录后
└── 对每个匹配目录分别应用同一份 layout
```

通用规则：

1. 使用 POSIX `/`，匹配区分大小写；
2. 禁止绝对路径、反斜杠、空字符串和 `..`；
3. 只有 `file_collection`、`directory_collection` 允许 glob；
4. 只有顶层 `directory` 可以使用 `path: "."` 表示 Scope 根；
5. `file_collection` 只匹配普通文件，`directory_collection` 只匹配目录；
6. 顶层节点和 `required=true` 的嵌套节点必须至少匹配一项；
7. `required=false` 可以不匹配，但一旦存在仍需满足格式和子布局。

### 7.4 四种物理组织

#### A. 单个文件 `file`

```json
{
  "kind": "file",
  "path": "standard.pdf",
  "format": "pdf",
  "content_validation": "strict"
}
```

```text
state/filesystem_scopes/specification/
└── standard.pdf
```

Scope 根中不能再有其他普通文件。单文件仍使用 Scope 目录，因为访问权限、任务复制和 Record 路径
都以 Scope 为边界。

#### B. 同类文件集合 `file_collection`

```json
{
  "kind": "file_collection",
  "path": "fixtures/**/*.xml",
  "format": "xml",
  "content_validation": "allow_invalid"
}
```

```text
state/filesystem_scopes/vast_fixtures/
└── fixtures/
    ├── valid/linear.xml
    └── invalid/missing_media.xml
```

所有普通文件都必须被顶层 glob 匹配。若目录中还需要 README、JSON 清单或其他格式，应改用
`directory`，在 `layout` 中分别声明每类文件。

#### C. 一个有层级的目录或项目 `directory`

```json
{
  "kind": "directory",
  "path": ".",
  "layout": [
    {
      "kind": "file",
      "path": "project.json",
      "description": "项目说明。",
      "required": true,
      "format": "json"
    },
    {
      "kind": "directory",
      "path": "src",
      "description": "项目源码目录。",
      "required": true,
      "layout": [
        {
          "kind": "file_collection",
          "path": "**/*.py",
          "description": "项目 Python 源码。",
          "required": true,
          "format": "python"
        }
      ]
    }
  ]
}
```

`layout` 是稳定结构模板，不是每个文件一条的索引。同格式文件使用 glob；但所有最终暴露的普通文件
都必须被某个 `file` 或 `file_collection` 节点覆盖。

#### D. 多个同构目录或项目 `directory_collection`

```json
{
  "kind": "directory_collection",
  "path": "projects/*",
  "layout": [
    {
      "kind": "file_collection",
      "path": "contracts/**/*.sol",
      "description": "一个项目中的 Solidity 合约。",
      "required": true,
      "format": "solidity"
    }
  ]
}
```

```text
state/filesystem_scopes/contracts/
└── projects/
    ├── project_a/contracts/**/*.sol
    └── project_b/contracts/**/*.sol
```

`projects/*` 匹配出的每个目录是一个集合成员。`layout` 对每个成员分别校验，只声明一次，不复制
多份 Schema。Record 若表示项目，可以保存 `projects/project_a` 并使用 `target=directory`；若表示
文件，则保存完整的 Scope 相对路径并使用 `target=file`。

### 7.5 如何划分 Scope

按下面顺序选择：

| 实际材料 | 选择 |
| --- | --- |
| 只有一个独立文件 | `file` |
| 多个文件格式和用途相同，不关心目录层级 | `file_collection` |
| 一个项目、数据包或混合格式目录 | `directory` |
| 多个结构相同、可按同一方式处理的项目 | `directory_collection` |
| 多个项目结构明显不同 | 按结构或工具用途拆成多个 Scope |

有限且已知的异构子目录也可以放在一个 `directory` 中分别声明多个分支；只有当它们共享访问权限、
任务复制边界和工具用途时才这样做。不要为了减少 Scope 数量而使用无法解释的宽泛 glob。

压缩包若由工具直接读取，按 `file` 声明为 `zip` 或 `tar`。若任务需要操作解包后的工程，则 Scope
保存确定性解包结果并按 `directory` 或 `directory_collection` 声明；原始压缩包不同时作为未说明
文件混入 Scope。

### 7.6 文件覆盖和安全

1. `file` Scope 只能包含声明的单个文件；
2. `file_collection` Scope 的所有普通文件都必须匹配顶层 glob；
3. 目录 Scope 中每个普通文件必须被某个叶子文件节点覆盖；
4. 不向任务暴露的缓存、构建产物、来源网页和下载日志在物化时排除；
5. Scope 禁止符号链接，防止解析后逃逸根目录；
6. Scope 不包含其他 Scope、任务输出或环境外状态；
7. 空目录不承载业务数据，除非工具确实依赖其存在，否则应删除。

### 7.7 `format` 与初始坏文件

`format` 使用小写稳定名称，不带前导点，也不写 Python 包名：

```text
json / jsonl / yaml / csv / parquet / sqlite / xml
pdf / docx / markdown / text / html
geojson / geopackage / shapefile
dxf / dwg / gdsii / lef / def
png / jpeg / tiff / svg / wav / mp3 / mp4
python / javascript / typescript / solidity / source_text
zip / tar
```

| `content_validation` | 含义 |
| --- | --- |
| `strict` | 文件必须通过扩展名、签名或轻量解析检查；默认值 |
| `allow_invalid` | 文件属于声明格式家族，但初始内容允许解析失败，用于诊断和修复任务 |

`allow_invalid` 仍要求路径和格式家族正确，不能用来保留 HTML 错页、下载错误或任意二进制内容。
若 Record 描述这些文件，应增加 `parse_status`、`validation_status` 等字段记录初始状态。

### 7.8 运行时访问

`read_only` Scope 可以直接挂载为只读；`copy_on_write` Scope 在任务开始时复制到隔离区。工具得到的
是 Scope 根和允许的相对路径，不得到环境根。任务新建文件属于任务输出，不自动改变
基线 `environment.json` 的 `structure`。

## 8. SQLite 物化

`state/records.sqlite` 是 SQLite 3 数据库，每个 Record Set 对应一张同名普通表。

| 逻辑类型 | SQLite 存储 | Loader 返回 |
| --- | --- | --- |
| `string` | `TEXT` | string |
| `integer` | `INTEGER` | integer |
| `number` | `REAL` | number |
| `boolean` | `INTEGER`，仅 `0/1` | boolean |
| `object` | `TEXT`，规范 JSON Object | object |
| `array` | `TEXT`，规范 JSON Array | array |

Record Set 不保存业务 BLOB；原始字节进入 Filesystem Scope。

发布前要求：`PRAGMA integrity_check` 返回 `ok`；不存在 `-wal`、`-shm`；每个 Record Set 有同名
表；字段与列完全一致；没有未声明表或列；值满足类型和约束；Object/Array 可以解码；非空
`key_fields` 唯一。数据库行顺序没有业务含义，工具必须显式排序。

## 9. Validator 最低检查

### 9.1 声明

```text
必填字段存在，没有未知字段
ID、字段名、枚举和类型参数合法
Object/Array 嵌套不超过两层
所有 Record Set、字段、Relationship 和 Scope 引用存在
```

### 9.2 记录

```text
SQLite 完整性、表和列一致
字段类型、范围、format、enum、const 和 nullable
Object/Array JSON 及嵌套定义
key_fields 唯一
Relationship 目标唯一、来源闭合、基数成立且有实际命中
```

### 9.3 文件

```text
Scope 根存在且互相隔离
路径不越界且没有符号链接
顶层和 required 节点有匹配项
所有普通文件被 structure/layout 覆盖
文件扩展名、格式家族和 content_validation 合法
Record 中的 filesystem_path 存在且目标类型正确
copy_on_write 只修改任务副本
```

JSON Schema 无法独立证明 SQLite 唯一性、Relationship 闭合、实际文件覆盖和路径存在性；这些必须
由包级 Validator 结合 `environment.json` 与 `state/` 检查。
