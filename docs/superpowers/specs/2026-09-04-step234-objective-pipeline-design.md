# Step 2-5 目标贯穿式任务生成流水线 PRD

## 1. 文档状态

- 状态：待评审
- 日期：2026-09-04
- 范围：`task_gen/tool_graph` 的 Step 2、Step 3、Step 4、Step 5
- 不改变：Step 0、Step 1、六阶段总体顺序、真实工具执行和最终 Task Schema

## 2. 背景

当前 Tool Graph 流水线先从工具图采样候选链，再执行链，最后依据真实执行轨迹生成任务。
这个方向能够保证最终任务存在一条真实参考轨迹，但各阶段对“这条链究竟要完成什么”缺少
稳定、共享的约束：

1. Step 2 主要审查工具之间是否连贯，但没有保存供后续阶段共同使用的业务目标。
2. Step 3 会根据完整链临时生成 `task_intent`，该意图不落盘，也不受 Step 2 约束。
3. Step 4 再次根据执行轨迹理解任务，可能将执行过程、偶然选择或失败结果重新包装为用户
   目标。
4. Step 5 只能比较最终任务与执行轨迹，无法判断它们是否共同遵守执行前确定的目标。

已有实验说明，在 Step 2 审查链时同时形成目标，并要求后续阶段遵循该目标，是一条可行
路径。实验也引入了完整 `chain_plan`、参数来源、事实摘要和 workspace 状态变化等结构，
但这些结构当前没有充分证据证明其收益，且实现复杂度较高。本次改造只保留已经形成共识的
最小机制。

## 3. 问题定义

本次要解决的核心问题不是“怎样提前生成完整任务”，而是：

> 在仍然先采样工具链的前提下，怎样让链审查、真实执行、任务生成和最终检查围绕同一个
> 业务目标工作，并在真实数据出现后只实例化目标，而不重新解释目标。

这里的业务目标不是最终任务文本。Step 2 尚未读取真实运行数据，因此只能生成一个
**目标模板**：它确定业务方向和预期结果类型，但允许 Step 3 将其中未知的对象和事实绑定为
真实值。

## 4. 产品目标

1. Step 2 对每条候选链形成一个统一、自然、可验证的业务目标模板。
2. Step 2 可以修订或拒绝候选链，避免无关、重复、冲突或无法获得必要输入的调用进入执行。
3. Step 3 直接使用 Step 2 的目标，不再独立生成另一份临时意图。
4. Step 3 根据前序真实调用结果逐步实例化目标；无法可靠继续时失败，不改变目标迁就数据。
5. Step 4 根据目标和真实执行轨迹生成结果导向的任务，不逐项复述调用过程，也不重新发明
   目标。
6. Step 4 保留一次受限反思，只改善任务表达，不承担规划或事实修补。
7. Step 5 独立检查目标、任务文本和真实调用结果是否一致。
8. 多样性保持为候选集合的选择策略，不干预单个候选的业务判断或运行时对象选择。

## 5. 第一性原则

### 5.1 统一目标

一条候选链必须能够解释为一个边界清楚的业务目标。每次主要调用都应对目标有独立且不重复
的贡献；查询、转换和验证可以构成贡献，但不能仅因链长要求保留无关调用。

### 5.2 事实有依据

关于环境既有状态的判断必须来自公开环境信息或已经观察到的真实工具结果。模型可以为完成
目标作合理选择并创建新内容，但不能把尚未观察到的环境状态当作事实。

### 5.3 语义与因果保持

后续阶段可以把目标中的未知对象绑定为真实对象，也可以改善自然语言表达，但不能改变业务
目标的含义。执行后才产生或观察到的信息不能伪装成执行前已经给定的用户要求。

### 5.4 用户视角

最终任务描述用户希望获得的业务结果和必要约束，而不是工具、调用顺序、参数传递或其他
实现机制。

### 5.5 确定性检查归代码

候选链中的工具名是否存在、字段类型、JSON 结构、链长、调用顺序和 Schema 等确定性条件
由代码检查。LLM prompt 只承担目标合理性、事实依据、语义一致性和自然表达等语义判断。

### 5.6 历史案例进入测试，不进入生产规则

生产 prompt 不枚举具体环境、工具、字段或历史失败样例。历史问题用于构造测试和固定轨迹
对照，不能逐条转写成不断增长的 prompt 条款。

## 6. 非目标

- 不交换 Step 2、Step 3、Step 4 的总体顺序。
- 不在 Step 2 前生成完整自然语言任务。
- 不引入完整 `chain_plan`、逐步用途或调用位置依赖。
- 不引入 `argument_sources`。
- 不引入 `resolved_facts`。
- 不比较或向 LLM 提供 initial/final workspace 状态变化。
- 不重构 Step 1 工具图或引入 prerequisite 模型。
- 不修改环境工具实现，也不在 TaskGen 中补偿环境工具契约错误。
- 不引入按候选槽位选择不同业务对象的 prompt 规则。
- 不新增外部依赖、数据库、规划服务或工作流框架。

## 7. 方案选择

### 7.1 方案 A：继续由 Step 3 临时生成意图

只加强现有 `task_intent` prompt，改动最小，但 Step 2 仍可能将没有可信业务目标的链送入
执行；Step 3 和 Step 4 仍然缺少稳定的共享目标。

结论：不采用。

### 7.2 方案 B：Step 2 输出完整结构化计划

为每个候选保存目标、目标选择、预期效果、逐步用途和逐步依赖。约束力强，但字段之间存在
大量重复，结构正确不等于语义正确，且已有记录没有充分验证完整结构的收益。

结论：本次不采用。

### 7.3 方案 C：Step 2 输出最小目标模板

Step 2 在同一次整链审查中输出修订后的 `chain` 和一个 `objective` 字符串。后续阶段共同
使用该目标，真实执行只负责绑定未知对象和事实。

优点：保留原架构，只新增一个跨阶段字段；能够消除重复生成意图，同时让 Step 4 和 Step 5
拥有明确的比较基准。

结论：采用。

## 8. 目标数据流

```text
Step 1 工具关系图
  -> Step 2 采样原始链
  -> Step 2 集合级结构多样性筛选
  -> Step 2 整链审查
       输出 accepted + revised chain + objective + reason
  -> Step 2 逻辑评分和审查后结构再平衡
  -> Step 3 按 objective 逐步填参并真实执行
       用真实结果绑定目标中的未知对象
  -> Step 4 按 objective + tool_calls/results 生成任务初稿
  -> Step 4 一次受限反思
  -> Step 4 生成参考答案和资源约束
  -> Step 5 检查 objective、task_text、tool_calls/results 一致性
  -> tasks.json / rejected.json
```

Step 0、Step 1、`pipeline.py` 的调用顺序和 AppendOnlyBundle 机制保持不变。

## 9. 核心数据契约

### 9.1 Step 2 候选

每个通过整链审查的候选只新增一个字段：

```json
{
  "task_id": "task1",
  "chain": ["list_items", "create_item", "read_item"],
  "objective": "基于一个实际发现的合格对象创建相关业务记录",
  "score": 8,
  "llm_review": {
    "original_chain": ["list_items", "create_item", "read_item"],
    "reason": "该链形成完整的发现、创建和确认流程",
    "error": null
  },
  "logic_score": 5,
  "logic_reason": "目标统一且调用共同服务该目标"
}
```

`objective` 是流水线内部字段，不进入最终 Task Schema。它会保留在中间 Bundle 和拒绝记录
中，便于分析目标在何处发生偏离。

### 9.2 目标模板约束

`objective` 必须：

- 描述一个结果导向的业务目标，而不是调用步骤。
- 与修订后的完整链共同成立。
- 允许用“一个实际存在的失败用例”“一个符合条件的会议”等描述尚待发现的对象。
- 说明链要实现的主要业务结果；辅助性的发现、转换或回读可以支撑执行，但不必写成用户目标。
- 不声称尚未执行就能知道的具体对象、ID、状态或统计结果。
- 不包含工具名、调用顺序或内部实现说明。

目标冻结的是业务语义，不是所有运行时变量。以下变化属于合法实例化：

```text
目标模板：为一个实际存在的失败测试建立、分类并关联一条缺陷
真实绑定：失败测试 = testApp，组件 = io.olamy.AlwaysFailTest
```

以下变化属于非法目标漂移：

```text
目标模板：建立并分类缺陷
执行失败后改写：只查询失败测试统计
```

### 9.3 Step 3 执行结果

保持现有 `execution` 结构，不增加事实摘要或状态变化：

```json
{
  "execution": {
    "success": true,
    "tool_calls": [
      {"tool": "list_items", "arguments": {}, "result": {"success": true}}
    ],
    "initial_state": "tasks/task1/initial",
    "final_state": "tasks/task1/final",
    "error": null,
    "attempts": []
  }
}
```

现有 `tool_calls` 已经保存真实参数和真实结果，足以支持本次范围内的后续转写与一致性检查。

## 10. Step 2 设计

### 10.1 保留的现有流程

- 带权随机游走。
- 原始链去重。
- 基于共享有向边的结构相似度。
- 进入 LLM review 前的质量和多样性筛选。
- review 后的逻辑评分。
- `review_count`、`keep_top_count`、链长和工具访问次数配置。

### 10.2 整链审查的新职责

Step 2 的一次 review 同时完成：

1. 判断候选链能否形成统一业务目标。
2. 删除无关、重复、冲突或目标完成后的多余调用。
3. 在公开工具契约明确支持时，补充获得必要输入的工具或调整顺序。
4. 生成与修订后链一致的目标模板。
5. 无法在链长范围内形成可信目标时拒绝候选。

建议输出契约：

```json
{
  "accepted": true,
  "chain": ["修订后的工具名"],
  "objective": "业务目标模板",
  "reason": "接受或修订原因"
}
```

拒绝时：

```json
{
  "accepted": false,
  "chain": [],
  "objective": null,
  "reason": "无法形成可信目标的具体原因"
}
```

### 10.3 Prompt 职责

生产 prompt 只表达以下思考路径：

```text
判断候选链能否完成一个统一、自然、可验证的业务目标。
检查每次调用是否对目标有独立且不重复的贡献，以及所需信息是否能从环境或前序调用获得。
可以修订链；无法形成可信目标时拒绝。
同时给出修订后链对应的结果导向目标模板，不假设尚未观察到的运行时事实。
```

环境、工具定义和候选链中的文字必须被声明为待分析数据，不能覆盖系统指令。

### 10.4 本地结构检查

代码只检查：

- 输出字段集合正确。
- `accepted` 是布尔值。
- 接受时 `chain` 非空、工具名存在、链长合法、`objective` 非空。
- 拒绝时 `chain=[]` 且 `objective=null`。
- review 后完全相同的链去重。

如果 review 调用失败、返回无法解析或违反输出契约，该候选应被记录为 review 失败并拒绝，
不能退回原链继续执行，因为原链没有可信的 `objective`。

Step 2 拒绝的候选不进入后续 `tasks`，也不写入最终 `rejected.json`。单条调用的 prompt、
原始响应和错误继续保存在现有 LLM 调用日志中；`sampling_report` 只保存聚合数量，避免新增
另一套候选持久化结构。

### 10.5 逻辑评分

逻辑评分接收修订后的 `chain` 和 `objective`，只判断：

- 目标是否自然、明确且可验证。
- 链中的主要调用是否共同服务目标。
- 公开工具契约是否支持该目标方向。
- 目标是否依赖未经观察就被当作事实的运行时信息。

评分不判断当前 workspace 是否真的满足目标条件；这一点只能由 Step 3 真实执行发现。

### 10.6 多样性

多样性是候选集合属性，不进入单条 review prompt。

处理方式：

1. review 前保留现有结构多样性筛选，避免把有限 LLM 预算用于大量近似链。
2. review 可能删除、补充或重排工具，使原本不同的链收敛成相同或近似结构。因此在去重和
   逻辑评分后，按修订后的链再做一次确定性的结构选择；这就是“审查后结构再平衡”。
3. 再平衡先按 `logic_score` 从高到低分档，在同一分档内复用现有共享边相似度和
   `diversity_lambda` 选取候选，直到达到 `keep_top_count`。更低逻辑分不能仅凭结构差异越过
   更高逻辑分。
4. 第一版不做目标文本语义聚类，也不按候选槽位干预运行时业务对象。

该步骤不增加 LLM 调用，也不判断业务目标是否相似；它只修复 review 改链后可能重新出现的
结构集中。

`sampling_report` 补充以下确定性指标：

- `review_rejected_count`：模型明确拒绝的候选数。
- `review_error_count`：调用或输出契约失败数。
- `post_review_unique_chain_count`：review 修改并去重后的唯一链数。
- `selected_unique_edge_count`：最终候选覆盖的不同有向边数量。

暂不增加目标文本语义聚类或目标多样性评分。

## 11. Step 3 设计

### 11.1 删除重复目标生成

删除每个候选执行前的 `_generate_intent` / `task_intent` LLM 调用。Step 3 直接读取 Step 2
保存的 `objective`。

这既减少一次 LLM 调用，也消除两个阶段分别解释同一条链造成的目标漂移。

### 11.2 参数生成输入

每次只为当前工具生成参数，模型获得：

```text
objective
完整 chain
当前工具及 inputSchema
completed_calls（含真实 arguments 和 result）
remaining_chain
previous_failure
公开环境信息
```

`completed_calls` 延续现有受限传输逻辑，避免大结果无限扩张 prompt，同时保留小型标识和
业务字段。

### 11.3 Prompt 职责

```text
根据既定目标、当前工具契约和真实执行进度生成当前调用参数。
关于环境既有状态的判断必须以公开信息或已观察结果为依据。
可以为完成目标作合理选择并创建必要的新内容。
如果缺少可靠依据，或真实情况已经使既定目标无法继续，返回明确错误，不改变目标。
```

prompt 不枚举 ID、标题、评论、状态或其他具体字段类型。模型应依据“既有事实”和“本次
行动产生的新内容”的区别作判断。

### 11.4 参数输出

成功：

```json
{"arguments": {}}
```

无法继续：

```json
{"error": "缺少必要事实或真实结果与目标冲突的具体原因"}
```

两种形状互斥。`error` 表示模型认为当前真实上下文不足以继续，本次不调用工具，也不通过
重新生成目标恢复候选。模型的语义判断不直接视为已证实事实：该错误和原上下文应进入现有
参数重试，让下一次生成能够复核判断；重试耗尽后才按候选失败处理。传输失败、解析失败和
Schema 错误同样沿用现有参数重试。

如果执行器能从已校验的工具结果或 Schema 约束直接确定调用无法成立，则可以按现有确定性
错误路径停止，不要求 LLM 重复判断。

### 11.5 真实结果优先级

`objective` 决定业务方向，但不能覆盖事实。发生以下情况时应失败：

```text
目标要求处理一个符合条件的对象
真实查询返回不存在符合条件的对象
```

以下情况属于正常实例化：

```text
目标要求处理一个符合条件的对象
真实查询返回多个候选
模型依据公开业务条件选择其中一个，并在后续始终使用该真实对象
```

第一版不要求记录结构化选择策略或参数来源。真实参数与调用结果已经保存在执行轨迹中，
出现问题时可以从轨迹复查。

### 11.6 重试和执行基础设施

工具沙箱、并发、超时、内存和写入限制保持现状。工具真实执行失败时沿用现有整链重试规则；
本次不重构执行器。

## 12. Step 4 设计

### 12.1 任务初稿

任务初稿生成使用：

```text
objective
environment public context
public tool definitions
chain
successful tool_calls with arguments and results
```

不增加 `resolved_facts` 或 workspace 状态差异。Step 4 直接从已有真实调用记录提取必要信息。

### 12.2 Prompt 职责

```text
把既定目标和真实成功执行转写为自然的用户任务。
任务应描述希望获得的业务结果，并提供执行前必须给出的业务信息。
保持目标含义和事实边界，不加入实现过程或偶然执行结果。
如果真实执行没有实现既定目标，返回失败，不能重新发明任务迁就轨迹。
```

“用户视角”是抽象原则，不在生产 prompt 或本地代码中维护工具名、路径、字段类别等历史
问题清单。本地检查只处理当前结构化上下文足以直接判定的情况；需要理解文本用途或业务
语境时，由 Step 5 按“任务不依赖实现机制”的原则作语义判断。

### 12.3 目标实例化

Step 4 可以把 Step 3 发现的真实对象写入具体任务，只要它是目标模板中未知对象的绑定，
而不是新增业务要求。例如：

```text
objective：为一个真实失败测试创建并分类缺陷
task_text：为 testApp 的“built to fail”失败创建并分类缺陷
```

Step 4 不得把失败轨迹改写成另一个更容易成立的任务：

```text
objective：创建并分类缺陷
实际执行：只读取失败测试
非法 task_text：查询失败测试详情
```

### 12.4 一次受限反思

反思位于任务初稿之后、参考答案之前：

```text
task_text draft
  -> task reflection
  -> reference_answer
  -> resource_constraints
```

反思只检查：

- 文本是否自然且结果导向。
- 必要业务信息是否充分。
- 是否保持目标和真实事实。
- 是否混入不属于用户目标的实现细节。

输出保持现有形状：

```json
{"analyze": "检查结论", "need_revision": false, "task_text": ""}
```

`need_revision=true` 时只允许在不改变目标和事实的前提下修改表达。反思不是第二次规划，不能
补救坏链或补造事实。`analyze` 用于本轮反思先陈述检查依据再作修改决定，不作为新的事实
来源，也不传入后续阶段。

反思属于增强步骤而非必要事实来源。反思调用失败或返回无效时保留任务初稿并继续，而不是
让一个已成功生成的候选失败。反思前后输出已由现有 LLM 调用日志记录，不新增专用审计字段。

### 12.5 参考答案和资源约束

现有生成顺序和输出字段保持不变，各步骤只接收完成本职工作所需的上下文：

- `reference_answer` 接收最终 `task_text` 和真实调用结果，必须回答任务并符合事实。
- `resource_constraints` 接收最终 `task_text` 和环境公开资源，根据任务语义生成，不从
  workspace 差异反推。

`objective` 已在任务初稿和反思阶段约束最终 `task_text`，不再重复提供给上述两个子步骤。

本次不改变正式 Task Schema 中这两个字段的表达方式。

## 13. Step 5 设计

### 13.1 范围边界

本次不扩展到 workspace 终态验收。Step 5 只在现有结构、Schema 和语义检查基础上增加
`objective` 这一比较基准。

### 13.2 本地确定性检查

保留现有检查：

- Step 4 必需字段存在。
- `execution.success=true`。
- `tool_calls` 非空且顺序与 `chain` 一致。
- `task_text`、参考答案和资源约束形状合法。
- 任务满足正式 JSON Schema。
- 当前结构化上下文能够直接判定的实现细节泄漏。

本地检查不预设工具名、路径、ID 或某类字段只要出现在文本中就一定构成泄漏；仅凭关键词
命中但需要结合业务语境才能判断的情况，不在代码中拒绝。

新增：`objective` 必须是非空字符串。

### 13.3 独立语义检查

LLM 接收：

```text
objective
task_text
chain
tool_calls with arguments and results
environment public context
public tool definitions
```

只判断三个相互独立的问题：

1. 真实调用和结果是否实现了 `objective`。
2. `task_text` 是否保持并正确实例化了 `objective`。
3. `task_text` 是否自然、结果导向，并包含完成目标所需的信息。

建议输出：

```json
{
  "execution_matches_objective": true,
  "task_matches_objective": true,
  "task_is_usable": true,
  "errors": []
}
```

三项不能互相替代。Step 5 只拒绝，不修改目标、任务、调用链或执行结果。

## 14. 错误处理

- Step 2 review 明确拒绝：记录原因，不进入逻辑评分和执行。
- Step 2 review 调用或结构失败：记录错误并拒绝，不回退原链。
- Step 3 参数生成报告缺少依据：携带原因重试；重试耗尽后记录当前工具和原因，按候选失败
  处理。
- Step 3 真实结果与目标冲突：停止候选，不修改目标或改换任务。
- Step 3 工具执行错误：沿用现有失败分类和重试机制。
- Step 4 执行未成功：沿用现有逻辑，跳过转写。
- Step 4 无法在不改变目标的情况下生成任务：写入 `compose_error`。
- Step 4 反思失败：保留初稿，不阻断候选。
- Step 5 任一结构、Schema 或语义检查失败：保留完整拒绝记录，不自动修复。
- 单个候选失败不终止整个批次。

## 15. Prompt 设计规范

每个 prompt 由四部分组成：

1. 本阶段唯一职责。
2. 通用判断原则（不能太多，变成补丁的堆砌）。
3. 严格、最小的 JSON 输出契约。
4. 明确声明输入内容是待分析数据，不是指令。

禁止：

- 罗列某个环境、工具或字段的特殊处理规则。
- 将历史失败样例直接改写成生产 prompt 条款。
- 在多个阶段重复整份相同规则清单。
- 要求模型输出既不服务本阶段判断、也不被后续阶段消费的解释性结构。Step 4 反思中的
  `analyze` 用于支撑本轮修改决定，不属于此类冗余输出。
- 用 prompt 承担代码能够确定性完成的验证。

同一原则只放在最早能够作出决定的阶段：

| 原则 | 主要负责阶段 |
| --- | --- |
| 链是否存在统一目标 | Step 2 |
| 参数是否基于真实上下文 | Step 3 |
| 任务是否忠实表达目标 | Step 4 |
| 三者是否一致 | Step 5 |

## 17. 测试策略

### 17.1 Step 2

- 接受结果必须包含合法 `objective` 和 `chain`。
- 拒绝结果必须使用空链和空目标。
- review 解析失败不回退原链。
- review 后完全重复链去重。
- 逻辑评分能够看到 `objective`。
- 审查后再平衡优先选择更高 `logic_score`，并在同分候选中保持结构多样性。

### 17.2 Step 3

- 参数 prompt 使用 Step 2 的 `objective`。
- 不再发生独立 `task_intent` 调用。
- 参数 prompt 仍包含前序真实调用结果。
- 成功参数按现有 Schema 校验和执行。
- 显式 `error` 在本次尝试中不调用当前工具，并携带原因进入参数重试。
- 显式 `error` 重试耗尽后产生可定位失败，不生成替代目标。
- 真实结果与目标冲突时不会生成替代目标。

### 17.3 Step 4

- 任务初稿和反思 prompt 使用同一 `objective`。
- 参考答案只依据最终任务和真实结果，资源约束只依据最终任务和公开资源。
- 执行失败候选不转写。
- 初稿无法保持目标时产生 `compose_error`。
- 反思不修改合格初稿。
- 反思可以在不改变目标的情况下修改表达。
- 反思调用失败时保留初稿并继续。

### 17.4 Step 5

- 缺少目标时确定性拒绝。
- 三个语义判断必须分别为真。
- 任务改变目标时拒绝。
- 执行没有实现目标时拒绝。
- 任务信息不足或表达为操作清单时拒绝。
- Step 5 不修补候选。

### 17.5 固定轨迹对照

使用固定候选链和固定工具返回结果进行前后对照，而不是只比较不同整轮运行的通过数量：

- 一条包含重复或目标完成后多余调用的链，应在 Step 2 被修订或拒绝。
- 一条需要前序返回值的链，应在 Step 3 使用真实结果完成参数绑定。
- 一条执行结果不满足目标的轨迹，不得在 Step 4 被包装成另一个任务。
- 一条抽象目标应在执行后合法绑定具体业务对象，而不被误判为目标漂移。

历史环境案例可以用于回归测试，但测试断言应表达上述通用性质，不将具体环境名称和样本值
写回生产 prompt。

## 18. 运行评估

实现后使用相同环境、模型、配置、随机种子和尽可能相同的候选链进行比较。至少记录：

- Step 2 review 接受、修订、拒绝和解析失败数量。
- review 前后唯一链数。
- 最终候选共享边相似度和工具边覆盖情况。
- Step 3 执行成功率及按失败类型分布。
- Step 4 初稿成功数、反思修改数和反思失败数。
- Step 4 因目标与真实结果不一致而拒绝的数量。
- Step 5 三项语义检查各自的失败数量。
- 每阶段 LLM 调用次数和耗时。

通过率不能单独证明质量提升。人工抽查至少判断：目标是否自然、链是否共同服务目标、执行
是否只实例化而未改变目标、最终任务是否忠实表达目标。

## 19. 完成条件

- Step 2 每个进入执行的候选都有非空 `objective`。
- Step 3 不再生成独立 `task_intent`，并继续使用前序真实调用结果。
- Step 4 的初稿和反思使用同一目标，参考答案和资源约束使用已经受该目标约束的最终任务。
- Step 4 不能将偏离目标的执行轨迹改写成另一个任务。
- Step 4 反思失败不会使有效初稿失败。
- Step 5 独立检查执行、任务与目标的一致性。
- 多样性不进入单候选 prompt，不影响业务对象的合理选择。
- 不新增 `chain_plan`、`argument_sources`、`resolved_facts` 或 `state_changes`。
- 相关单元测试通过，固定轨迹对照覆盖目标形成、实例化和漂移三类路径。
- README 与最终实现保持一致。

## 20. 已知限制与后续条件

1. Step 2 看不到真实 workspace，无法保证目标一定可执行。Step 3 发现不满足条件后拒绝是正常
   行为，不应让 Step 2 假装预知事实。
2. 不使用 workspace 状态变化时，流水线只能依据工具返回结果判断执行效果。只有实际运行
   证明这一证据不足，才重新设计确定性终态检查。
3. 不保存参数来源时，事实依据只能从原始调用轨迹人工复查。只有出现无法定位的重复问题，
   才考虑增加最小来源字段。
4. 链结构多样性不等于业务目标多样性。只有运行报告显示大量不同链持续生成同质目标，才
   引入目标级去重或分类；第一版不做语义聚类。
5. 一次反思增加调用成本。通过反思修改率、人工改善率和耗时判断是否继续保留，不继续叠加
   第二轮反思。

## 21. 实施顺序建议

1. 先调整 Step 2 契约和测试，使 `objective` 成为进入 Step 3 的必要字段。
2. 再调整 Step 3，删除临时意图并消费 `objective`。
3. 调整 Step 4 的目标贯穿和非阻断反思。
4. 最后调整 Step 5 的三方一致性检查。
5. 运行固定轨迹对照，再进行完整环境探针。

每一步应保持单独可测试，不同时引入未在本 PRD 中定义的证据结构或工具图重构。
