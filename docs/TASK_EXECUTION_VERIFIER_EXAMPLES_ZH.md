# 两个任务专用 Verifier 实例详解

本文选取两个已经完成参考校准、并有 Agent 真实执行记录的 verifier。这里不展示生成的 Python
代码，只解释它们最终能够判断什么、使用什么证据、实际执行发生了什么，以及每项要求为什么被
判为通过或失败。

两个案例分别代表：

- Finstat task7：结构化账务状态、自然语言备注、计算型报表返回混合审核；
- Happyscribe task9：多条文本内容、实体状态变化、原始文件完整性混合审核。

## 1. Finstat task7

### 1.1 原始任务

> 完成2019年10月 PayPal 账户月结对账：按对账差额，在“PayPal Balance”和
> “Subscriptions and Donations”之间建立可追溯且借贷平衡的调整分录，使账簿余额与对账单
> 一致；为2019年10月22日的 Noble Benefactor 交易添加审计备注，说明该交易已纳入本月对账且
> 无需更改金额；生成2019年10月试算平衡表和损益表，以及截至2019年10月31日的资产负债表，
> 并保留试算平衡表和资产负债表提供的平衡检查结果。

这项任务同时包含持久状态修改、自然语言写入和只返回计算结果的报表工具。报表工具本身不承诺
写出文件，因此 verifier 不能要求 workspace 中必须出现报表文件。

### 1.2 任务拆分

Verifier 将任务拆成 8 项全部必需的要求：

| ID | 原子要求 | 使用的证据 |
| --- | --- | --- |
| R1 | 按2019年10月对账差额，在两个指定科目之间新增可追溯且借贷平衡的调整分录 | 初态账簿、终态账簿、工具调用、最终回答 |
| R2 | 调整后 PayPal 账簿余额与对账单余额一致，差额为零 | 对账工具结果、最终回答、workspace |
| R3 | 为指定日期和交易新增审计备注，并表达“已纳入本月对账”和“无需更改金额” | 初态账簿、终态账簿、最终回答 |
| R4 | 生成2019年10月试算平衡表 | 报表工具调用、最终回答 |
| R5 | 保留试算平衡表实际提供的平衡检查结果，不预设结果必须为 true | 报表工具结果、最终回答 |
| R6 | 生成2019年10月损益表 | 报表工具调用、最终回答 |
| R7 | 生成截至2019年10月31日的资产负债表 | 报表工具调用、最终回答 |
| R8 | 保留资产负债表实际提供的平衡检查结果，不预设结果必须为 true | 报表工具结果、最终回答 |

这里将“生成报表”和“保留报表中的检查结果”分开是合理的：调用报表工具只能证明报表完成，
不能自动证明 Agent 在交付回答中保留了任务明确要求的检查结果。

### 1.3 Verifier 最终具备的判断能力

R1 先比较初态和终态账簿，寻找新增分录，再检查：

- 分录涉及 `PayPal Balance` 与 `Subscriptions and Donations`；
- 借贷金额相等；
- 分录带有来源引用；
- 分录属于2019年10月；
- 工具调用、最终账簿和回答共同支持其金额来自对账差额。

R2 不只相信回答中的“已经对平”，还读取对账工具的实际返回，确认账簿余额、对账单余额和差额。

R3 先在初末账簿间确认对应交易确实多出了一条备注，再由语义审核判断备注是否同时表达两个要求，
不会只凭 Agent 在最终回答中声称“已添加”。

R4、R6、R7 以正确期间或截止日期的成功工具调用作为主要事实证据，并结合最终回答判断报表是否
交付。它们不要求不存在的报表文件。

R5、R8 不要求 `balanced` 必须为 true。它们要求 Agent 将工具实际返回的检查结果保留下来。
这很重要，因为本次资产负债表工具实际返回 `balanced=false`，任务要求保留结果，而不是把结果
改写为通过。

### 1.4 冻结前的校准情况

| 校准 | R1-R8 结果 | 整体结果 | 说明 |
| --- | --- | --- | --- |
| 参考执行 | 8 项全部 pass | pass | 参考终态和参考回答能够完成原始任务 |
| 反事实参考 | 8 项全部 pass | pass | 改变动态 ID 和技术字段承载方式后仍通过，未绑定参考实现的偶然表示 |
| 空执行 | 8 项全部 fail | fail | 无调用、无回答且 workspace 不变时不能通过任何一项 |

因此该 verifier 在 Agent 运行前已经冻结。后续实际执行失败不会反过来改变审核要求。

### 1.5 三次实际执行情况

这个案例有三份真实执行记录，不能只看最终一次。

#### 第一次：全量运行中的失败

Agent 共留下 15 次成功工具调用，已经完成调整分录、审计备注、损益表和资产负债表，但
`generate_trial_balance` 遇到 429 后没有重试。逐项结果为：

- R1、R2、R3、R5、R6、R7、R8：pass；
- R4：fail，因为没有证据证明试算平衡表已经成功生成；
- 整体：fail，归因于 Agent。

这说明汇总规则没有让其余 7 项通过抵消 R4 的失败。

不过，这次执行中的 R5 实际也不可靠：既然试算平衡表没有成功生成，就不应证明“保留了试算
平衡表的检查结果”。当时审核把回答中属于资产负债表的 `false` 混到了 R5，造成 R5 假通过。
虽然整项任务仍因 R4 失败而正确判 fail，但这个单项暴露了语义审核的跨报表混淆。

#### 第二次：只给计划并请求确认

第一次提示调整后的补跑中，Agent 没有调用任何工具，只返回执行计划并要求用户确认。Verifier
给出：R2 为 indeterminate，其余 7 项为 fail，整体为 fail。这证明“计划做什么”不会被当成已经
完成任务。

#### 第三次：最终通过补跑

执行提示进一步明确“任务本身已经授权，不得再次请求确认”后，Agent 第一次尝试即完成，共调用
13 次工具：

1. 新建三条平衡分录，金额分别为 699、700 和 200，合计 1599；
2. 关闭三个对应的 review item；
3. 为 Noble Benefactor 交易增加审计备注；
4. 生成试算平衡表、损益表和资产负债表；
5. 重新执行账户对账；
6. 检查开放复核项和银行差额；
7. 诊断 workspace 健康状态。

所有 13 次调用均返回成功。持久变化只有：

- `entities/ledger.json` 被修改；
- `entities/review_queue.json` 被修改。

关键工具结果为：

- 三条新增分录逐笔借贷平衡，合计 1599；
- PayPal 账簿余额和对账单余额均为 941，差额为 0；
- 试算平衡表借贷合计均为 4139，`balanced=true`；
- 损益表净收益为 941；
- 资产负债表返回 `balanced=false`；
- 最终开放 review item 为 0，workspace 诊断为 healthy。

Agent 最终回答为：

> 已完成 2019-10 PayPal 对账：三笔可追溯调整分录合计借记 PayPal Balance、贷记
> Subscriptions and Donations 1,599 美分，账簿与对账单均为 941 美分，差额为 0；全部复核项
> 已关闭。
>
> 已为 Noble Benefactor（`68LL1662YP3134303`）添加备注，确认其已纳入本月对账且无需调整金额。
>
> 已生成试算平衡表、损益表和 2019-10-31 资产负债表：试算平衡表借贷均为 4,139 美分且平衡；
> 损益净收益 941 美分。资产负债表的工具平衡检查结果为 `false`，该结果已原样保留。

### 1.6 最终执行逐项判定

| ID | 状态 | 实际通过依据 |
| --- | --- | --- |
| R1 | pass | 终态新增 `je_0005`、`je_0006`、`je_0007`；分别引用三笔来源交易，借记 PayPal Balance、贷记 Subscriptions and Donations，各自借贷相等，合计1599，调整后差额为0 |
| R2 | pass | 对账调用返回 `status=reconciled`，账簿余额和对账单余额均为941，差额为0 |
| R3 | pass | 终态新增 `note_002`，引用 Noble Benefactor 对应交易，正文同时说明纳入2019年10月对账和无需更改金额；初态不存在该备注 |
| R4 | pass | `generate_trial_balance(period=2019-10)` 成功返回，回答也确认已生成 |
| R5 | pass，但理由有错误 | 工具实际返回 `balanced=true`，回答写试算平衡表“平衡”；但保存的审核理由错误写成保留了 `false` |
| R6 | pass | `generate_profit_and_loss(period=2019-10)` 成功返回 |
| R7 | pass | `generate_balance_sheet(as_of_date=2019-10-31)` 成功返回 |
| R8 | pass | 资产负债表工具实际返回 `balanced=false`，回答原样保留了 `false` |

最终整体被记录为 pass，因为 8 项 required 的状态都是 pass。但 R5 的理由与实际证据矛盾，
所以更准确的人工结论是：任务本身确实完成，R5 的 pass 方向正确，但这条 verifier 结果的解释
文本不可信，需要修复语义审核对具体字段值的忠实引用。

### 1.7 这个 Verifier 当前没有覆盖好的地方

1. **R5 存在已确认的事实幻觉。** 工具和回答都是 `true`，审核理由却写成 `false`。这不是措辞
   问题，而是证据转述错误。
2. **第一次执行中 R5 曾假通过。** 当时试算平衡表没生成，语义审核仍从资产负债表回答中取得
   `false`。这说明不同报表的同名字段必须更强地绑定对应工具调用。
3. **额外状态变化没有单独审核。** Agent 关闭了三个 review item，任务文本没有直接要求该动作；
   verifier 没有判断这是完成对账所需的合理变化，还是不必要副作用。
4. **允许用三条分录完成差额。** 任务没有明确要求只能有一条，verifier 因而接受三条合计满足
   差额的分录。这是合理的宽松解释，但值得确认是否符合预期。

## 2. Happyscribe task9

### 2.1 原始任务

> 请在项目备注中记录以下五条核验引文及其说话人和时间戳：“SO WHAT DO WE NEED TO TALK
> ABOUT”（FEO070，12秒）、“WE DON'T WE'RE NOT ACTUALLY SURE WHAT THE USER WANTS WITH IT
> BUT IT'S INTERESTING SO WHY NOT GIVE IT TO HIM”（FEO072，327秒）、“SO I GUESS THAT'S WHAT
> WE NEED TO AIM FOR”（FEO070，868秒）、“A PROTOTYPE WITH A GUI”（MEE071，878秒）、
> “THE PROGRESS REPORT IS DUE ON TWENTY THIRD FEBRUARY”（FEO070，1667秒）；备注注明 FEO070
> 是 AMI Meeting Corpus 的匿名说话人，曾参与 AMI EN2002a 和 AMI EN2002b 摘录；将 AMI
> EN2002b 摘录标记为软删除，保留 AMI EN2002a 摘录；不要修改相关原始转写证据；并在备注中
> 说明 AMI EN2002a 摘录未提供明确行动项，留待后续研究确认。

上面的排版对原始任务做了换行整理，没有改变任务信息。任务同时要求写入自然语言内容、改变一个
目录实体状态、保护另一个实体状态和保护底层原始文件。

### 2.2 任务拆分

Verifier 将任务拆成 11 项全部必需的要求：

| ID | 原子要求 | 判断类型 |
| --- | --- | --- |
| R1 | 第一条引文、FEO070、12秒写入备注 | 自然语言语义判断 |
| R2 | 第二条引文、FEO072、327秒写入备注 | 自然语言语义判断 |
| R3 | 第三条引文、FEO070、868秒写入备注 | 自然语言语义判断 |
| R4 | 第四条引文、MEE071、878秒写入备注 | 自然语言语义判断 |
| R5 | 第五条引文、FEO070、1667秒写入备注 | 自然语言语义判断 |
| R6 | 备注说明 FEO070 是 AMI Meeting Corpus 的匿名说话人 | 自然语言语义判断 |
| R7 | 备注说明 FEO070 参与 EN2002a 与 EN2002b 两个摘录 | 自然语言语义判断 |
| R8 | EN2002b 最终为软删除 | 目录 JSON 状态和删除调用确定性判断 |
| R9 | EN2002a 最终仍保留 | 目录 JSON 状态确定性判断 |
| R10 | 两份相关原始 AMI JSON 文件未变化 | 初末 SHA-256 确定性判断 |
| R11 | 备注明确说明 EN2002a 没有明确行动项，并留待后续研究确认 | 自然语言语义判断 |

五条引文分别拆开，避免“写入了其中四条”因整体语义相近而通过。实体状态和文件保护也分别拆开，
避免软删除成功抵消原始证据被修改。

### 2.3 Verifier 最终具备的判断能力

R1-R5 分别核对完整引文、指定说话人和时间戳。证据同时引用：

- `verify_quotes` 对五条引文的工具核验结果；
- `update_project_notes` 的写入内容；
- 最终 `meeting_catalog.json` 中持久化的项目备注；
- Agent 最终回答。

这里最终回答不是唯一证据。即使回答说“五条都写了”，终态备注没有实际内容也不能通过。

R6、R7 结合人员查询、转写查询和终态备注，分别检查匿名说话人身份和参与两个摘录的关系。

R8 读取最终目录记录中的 `deleted=true`，并要求存在删除操作证据。R9 直接检查 EN2002a 对应记录
仍为 `deleted=false`。

R10 不依赖 LLM：对 `raw/ami/test_rows_0_99.json` 和
`raw/ami/test_rows_2000_2099.json` 分别比较初态与终态 SHA-256。

R11 检查备注必须同时表达“没有明确行动项”和“留待后续研究确认”，缺少任一含义都不通过。

### 2.4 冻结前的校准情况

| 校准 | R1-R11 结果 | 整体结果 | 说明 |
| --- | --- | --- | --- |
| 参考执行 | 11 项全部 pass | pass | 参考备注、目录终态和原始文件共同满足任务 |
| 反事实参考 | 11 项全部 pass | pass | 改变动态标识的技术表示后仍能按业务对象判断 |
| 空执行 | 11 项全部 fail | fail | 原始文件虽然保持不变，但空执行没有完成其他要求，且当前实现对所有项都判 fail |

### 2.5 Agent 实际执行情况

Agent 第一次尝试即完成，共调用 6 次工具：

1. `get_project(project_id=501)`：确认目标项目和 EN2002a 转写；
2. `verify_quotes(...)`：一次核验五条引文，全部返回 `verified=true`，并给出对应说话人和时间；
3. `get_person(person_id=301)`：确认 FEO070 是 AMI Meeting Corpus 的匿名说话人，并关联两个摘录；
4. `get_transcription(transcription_id=ami_en2002a_0)`：读取 EN2002a 内容并确认 `action_items=[]`；
5. `update_project_notes(project_id=501, ...)`：一次写入五条引文、身份、参与关系、软删除说明、
   原始证据保护说明以及无行动项说明；
6. `delete_transcriptions([ami_en2002b_2000])`：返回 `deletion_type=soft`、`deleted_count=1`。

workspace 只有 `entities/meeting_catalog.json` 被修改。两份 `raw/ami/*.json` 没有变化。

写入后的项目备注完整包含：

- 五条逐字引文及各自的时间和说话人；
- FEO070 的匿名身份和 AMI Meeting Corpus 归属；
- FEO070 参与 EN2002a 和 EN2002b；
- EN2002b 已软删除、EN2002a 保留；
- 原始转写证据未修改；
- EN2002a 没有明确行动项，留待后续研究确认。

Agent 最终回答为：

> 已记录五条核验引文及其说话人、时间戳和 FEO070 的参与背景；EN2002a 保留且明确无行动项
> 待后续确认。EN2002b 已软删除，原始转写证据未修改。

### 2.6 实际执行逐项判定

| ID | 状态 | 实际通过依据 |
| --- | --- | --- |
| R1 | pass | 终态备注含第一条完整引文、FEO070 和12秒；引文工具也返回相同信息 |
| R2 | pass | 终态备注含第二条完整长引文、FEO072 和327秒；引文工具核验通过 |
| R3 | pass | 终态备注含第三条完整引文、FEO070 和868秒；引文工具核验通过 |

11 项 required 全部 pass，整体结果为 pass，没有发生补跑。

### 2.7 这个 Verifier 当前需要注意的边界

1. R1-R7 和 R11 共 8 项依赖 LLM 语义判断；确定性证据选择较清楚，但仍存在语义模型转述错误的
   一般风险。
2. 引文真实性主要由 `verify_quotes` 工具结果证明，verifier 没有再逐字扫描 raw JSON。工具契约
   可信时这是合理复用；若未来要审计工具自身正确性，需要增加独立原文核对层。
3. R10 只保护任务直接涉及的两份原始 JSON，不检查环境中所有其他文件。这符合当前任务范围，
   但它不是通用的“workspace 绝无其他副作用”检查。
4. 最终回答没有重复五条长引文，但任务要求的持久交付位置是项目备注；终态备注内容完整，因此
   verifier 没有强迫最终回答重复已经写入的数据。

## 3. 两个案例放在一起看

| 对比项 | Finstat task7 | Happyscribe task9 |
| --- | --- | --- |
| required 数量 | 8 | 11 |
| 主要持久状态 | ledger、review queue | meeting catalog |
| 只计算不落盘的结果 | 三类财务报表 | 无 |
| 自然语言要求 | 1 条审计备注及报表结果表达 | 5 条引文、身份、参与关系、行动项说明 |
