# Agent-World Mini 四阶段产物契约 v1.0

## 1. 设计依据

本文面向以下实际流水线：

```text
SeedArtifact
    │
    ▼
DatabaseEnvironmentArtifact                对应论文中的 D(m)
    │
    ├── 与 SeedArtifact 一起交给工具阶段
    ▼
ExecutableEnvironmentArtifact              对应论文中的 (D(m), F(m))
    │
    ▼
TaskArtifact                               对应 Xgraph 或 Xprog
```

论文 `2604.18292v1.pdf` 的核心定义是：

```text
主题 m
→ Agentic Database Mining 生成数据库 D(m)
→ Tool Generation 以 (m, D(m)) 生成工具集 F(m)
→ 最终环境 e = (D, F)
→ Task Synthesis 消费数据库描述和工具 Schema
```

因此不再设计一个不断堆字段的“万能环境 JSON”。每一阶段只保存下一阶段真正需要的内容，跨阶段通过 ID 和 SHA-256 引用，避免重复复制。

一个字段只有满足下面至少一项，才允许进入核心契约：

```text
1. 下游生成阶段必须读取它，才能生成正确产物；
2. Runtime/Agent/Verifier 必须读取它，才能执行任务；
3. Loader/Validator 必须读取它，才能复现或校验产物版本。
```

只用于页面展示、离线统计、调试日志，或者能从其他字段无歧义推导出的信息，不进入核心契约。

## 2. 四个阶段的接口

| 阶段 | 输入 | 输出 | 下一阶段为什么需要它 |
| --- | --- | --- | --- |
| 种子整理 | MCP、工具文档或工业 PRD | `SeedArtifact` | 指定真实主题、能力线索和研究起点 |
| 环境生成 | `SeedArtifact` | `DatabaseEnvironmentArtifact` | 提供真实数据库/文件、目录说明和可校验初始状态 |
| 工具生成 | `SeedArtifact + DatabaseEnvironmentArtifact` | `ExecutableEnvironmentArtifact` | 生成并验证数据库有依据、可执行的工具集 |
| 任务合成 | `ExecutableEnvironmentArtifact` | `TaskArtifact[]` | 基于真实工具执行和数据库状态生成可验证任务 |

## 3. 通用规则

四种产物都使用：

```text
JSON-native 值
JSON Schema Draft 2020-12
相对 POSIX 路径
SHA-256 内容指纹
显式 schema_version
```

跨产物引用统一为：

```json
{
  "id": "被引用产物的稳定 ID",
  "sha256": "被引用产物 JSON 的规范化 SHA-256"
}
```

`sha256` 用来保证任务、工具和数据库对应的是同一个不可歧义版本，不能只靠路径或名称关联。产物内引用的文件还要有自己的 `sha256`；这样从任务引用开始可以递归校验完整环境、数据库文件、工具代码和测试文件。

产物 JSON 使用 RFC 8785 JSON Canonicalization Scheme 后计算 SHA-256，普通文件直接对原始 bytes 计算 SHA-256。所有 `path/root` 都是相对产物包根目录的 POSIX 路径，禁止绝对路径、`.` 和 `..` 路径段。

除联合分支明确说明不出现的字段外，示例中的字段都为 required，不使用大量 `null` 表示“不适用”。核心数组的基数固定如下：

```text
Seed.anchors                              >= 1
anchors[].tool_clues                      >= 0
Database.database.entries                 >= 1
Database.database.rules                   >= 0
Database.sources                          >= 1
Executable.tools                          >= 1
Executable.tool_bindings                  与 tools 一一对应
Task.available_tools                      >= 1，且都是 Executable.tools 中的名称
Graph reference_solution.value            >= 1 次真实工具调用
```

四种 JSON 是 manifest，不会把真实数据文件或 Python 代码内嵌进去。对应产物包最少包含：

```text
Seed package:         seed.json
Database package:     database_environment.json + database/
Executable package:   executable_environment.json + runtime/ + tools/ + tests/
Task package:         task.json + 可选的 solutions/ 和 verifiers/
```

## 4. 第一阶段：`SeedArtifact`

### 4.1 Schema

```json
{
  "artifact_type": "seed",
  "schema_version": "1.0",
  "seed_id": "smithery_memory_bank",
  "name": "Memory Bank",
  "description": "A persistent project-memory workspace for maintaining context, decisions and progress.",
  "anchors": [
    {
      "kind": "mcp_server",
      "uri": "https://smithery.ai/server/example",
      "description": "Reference MCP server and its documented capabilities.",
      "tool_clues": [
        {
          "name": "read_memory",
          "description": "Read one memory document.",
          "inputSchema": {
            "type": "object",
            "properties": {
              "filename": {"type": "string"}
            },
            "required": ["filename"],
            "additionalProperties": false
          },
          "outputSchema": null
        }
      ]
    }
  ]
}
```

### 4.2 字段用途

| 字段 | 谁产生 | 谁消费 | 用途 | 为什么不能删除 |
| --- | --- | --- | --- | --- |
| `artifact_type` | 种子整理器 | Loader | 固定为 `seed` | 让 Loader 选择正确 Schema |
| `schema_version` | 种子整理器 | 全部下游 | 种子结构版本 | 防止不同版本字段被误读 |
| `seed_id` | Catalog | 环境、工具和审计阶段 | 稳定关联该主题的所有产物 | 名称可能重复或变化 |
| `name` | Catalog/人工 | Research Agent、人工审阅 | 简短主题名 | Research 需要清晰主题锚点 |
| `description` | Catalog/主题整理模型 | Research Agent、工具生成器 | 描述现实产品、工作流和范围 | 只看名称无法确定研究边界 |
| `anchors` | Catalog | Research Agent、工具生成器 | 保存 MCP、文档或 PRD 原始锚点 | 后续必须知道能力线索来自哪里 |
| `anchors[].kind` | Catalog | Research Agent | `mcp_server/tool_documentation/industrial_prd` | 不同来源需要不同研究策略 |
| `anchors[].uri` | Catalog | Research Agent、审计 | 真实起始地址 | 保证主题可追溯 |
| `anchors[].description` | Catalog | Research Agent | 说明该锚点提供什么信息 | URI 本身通常不可读 |
| `anchors[].tool_clues` | MCP/文档解析器 | 工具生成器 | 原能力线索，不是最终工具 | 论文工具生成同时依赖 `m` 和 `D` |

`tool_clues` 可以为空。每条 clue 只保存 `name/description/inputSchema/outputSchema`；两个 Schema 可以为 `null`，因为不少 PRD 或文档只有自然语言接口描述。许可、抓取日志和页面缓存属于数据采集审计产物，不是 Seed 到环境生成器的必需输入，因此不进入核心 Seed 契约。

种子中不保存：

```text
研究得到的数据
最终工具
数据库 Schema
任务
taxonomy 分类
```

taxonomy 是环境生态构建后的独立索引，不参与单环境执行。

## 5. 第二阶段：`DatabaseEnvironmentArtifact`

该产物是不带工具的环境，对应论文中的数据库 `D(m)`。这里的“数据库”包括结构化记录和文件，不限于关系表。

### 5.2 顶层字段用途

| 字段 | 谁产生 | 谁消费 | 用途 | 为什么不能删除 |
| --- | --- | --- | --- | --- |
| `artifact_type` | 环境生成器 | Loader | 固定为 `database_environment` | 区分种子、完整环境和任务 |
| `schema_version` | 环境生成器 | Loader、工具生成器 | 不带工具环境结构版本 | 支持单独升级数据库契约 |
| `database_environment_id` | 环境生成器 | 工具阶段、Loader | 该数据库环境的稳定 ID | 同一种子可以生成多个数据库版本，必须可分别引用 |
| `seed_ref` | 环境生成器 | 工具生成器、审计 | 指向实际使用的种子版本 | 工具生成需要论文中的 `(m, D)`，但无需复制种子 |
| `name` | 环境生成器 | 工具生成器、TaskGen、人工审阅 | 简短环境名 | 用于 Prompt 和产物索引 |
| `description` | 环境生成器 | 工具生成器、TaskGen | 说明数据库模拟的现实工作空间 | 工具和任务不能只靠文件名理解环境 |
| `database` | Research Agent/环境生成器 | Runtime、工具生成器、TaskGen、Verifier | 论文中的 `D(m)` | 是全部工具执行和状态验证的基底 |
| `sources` | Research Agent | 审计、工具生成器 | 数据和 fixture 血缘目录 | 防止模型编造数据库内容 |

### 5.3 `database.entries` 字段用途

| 字段 | 用途 | 下游消费者 |
| --- | --- | --- |
| `path` | 相对 `database.root` 的稳定路径 | Runtime、工具代码、Verifier |
| `kind` | `file/directory` | Loader |
| `role` | `primary_data/index/configuration/reference/fixture` | 工具生成器、TaskGen |
| `description` | 说明内容和现实用途 | 工具生成器、TaskGen |
| `media_type` | MIME 类型 | Runtime、解析器选择 |
| `sha256` | 初始内容指纹 | reset、完整性校验、任务绑定 |
| `source_refs` | 指向一个或多个 `sources[].source_id` | 审计；生成 fixture 也必须说明依据 |
| `mutable` | 工具是否允许改变该路径 | Runtime 写入边界、Verifier |
| `content_contract` | 内容如何校验 | Runtime、工具生成器、ToolGraph、Verifier |

数据库其余嵌套字段：

| 字段 | 用途 | 下游消费者 |
| --- | --- | --- |
| `database.root` | 产物包内数据库基线目录 | Loader、Runtime |
| `database.entries` | root 下必须存在的文件和空目录清单 | Loader、Validator、工具生成器 |
| `database.rules` | 无法只靠文件格式表达的跨字段或变更规则；允许空数组 | 工具生成器、工具测试、Verifier |
| `rules[].rule_id` | 稳定引用某条规则 | 测试报告、错误信息 |
| `rules[].description` | 可执行工具必须遵守的业务不变量 | 工具生成器、测试生成器 |
| `rules[].paths` | 规则影响的相对路径 | 工具生成器、Validator |
| `sources[].source_id` | 供 entries 复用的来源 ID | `source_refs` 解析、审计 |
| `sources[].uri` | 原始网页/API，或确定性生成器 URI | Research 审计、工具生成器 |

`content_contract` 是一个带类型的联合结构：

```text
json_schema       JSON 文件，保存完整 JSON Schema
tabular           CSV/Parquet 等表格，保存列和行约束
text              文本文件，保存 encoding
registered_format GDS、Touchstone、网表等专业格式，保存 validator_id
opaque             只校验 media_type、size 和 sha256
```

五种分支只保存各自真正需要的字段：

```json
{
  "kind": "json_schema",
  "schema": {"type": "object"}
}
```

```json
{
  "kind": "tabular",
  "format": "csv",
  "columns": [
    {
      "name": "wafer_id",
      "schema": {"type": "string", "minLength": 1}
    },
    {
      "name": "yield",
      "schema": {"type": "number", "minimum": 0, "maximum": 1}
    }
  ]
}
```

```json
{
  "kind": "text",
  "encoding": "utf-8"
}
```

文件 entry 必须包含 `media_type/sha256/source_refs/content_contract`。目录 entry 只用于声明必须预建的空目录，不包含这些文件字段。`sha256` 是初始文件内容的哈希，不是任务执行后的哈希。

GDS 示例：

```json
{
  "kind": "registered_format",
  "format": "gdsii",
  "validator_id": "gdsii_stream_v1"
}
```

这取代强制的“实体 Schema”。只有 JSON/表格条目需要结构化字段 Schema；专业二进制文件由专业 parser/validator 检查。

`database.root` 是只读基线目录。Runtime 启动每个工具测试、参考解和 Candidate Agent rollout 时，都把该目录复制到独立临时工作区。这个 reset 行为是全局协议，不允许每个环境自行选择，因此不再保存冗余的 `reset.strategy`。文件列表和每个文件的 `sha256` 已经构成初始状态清单，也不再额外保存一个可推导的 `manifest_sha256`。

### 5.4 为什么不再保存这些字段

| 不保存的字段 | 原因 |
| --- | --- |
| `state_space_definition` | 文件环境没有统一实体空间；结构已经在每个 entry 的 `content_contract` 中 |
| `data_type_definitions` | 会与 entry content contract 和工具 input/output Schema 重复 |
| `capability_definitions` | 能力线索已经在 Seed 中，最终能力由已验证工具决定 |
| `initial_state` | 初始数据库就是 `database.entries` 指向的快照，不再复制一份 JSON 状态 |
| `state_schema` | 文件树由 manifest 校验；JSON 条目由各自 content contract 校验 |
| `resources` | 所有初始资源就是数据库 entries，不维护第二份资源列表 |
| `provenance` | 已收敛为 `sources + entries[].source_refs` |
| `internal` | 第二阶段尚无工具内部信息，不需要空占位 |
| `execution_profile` | 工具依赖尚未生成，环境阶段无法给出最终可执行依赖；移到完整可执行环境 |
| `reset` | 每次运行都复制数据库基线是统一协议，不是单环境可变配置 |

### 5.5 实体信息什么时候才需要

实体不是环境顶层协议，也不是所有数据库必须经历的抽象。环境生成器只在数据本身确实由稳定、重复的业务记录组成时，才把记录字段写进对应文件的 `content_contract`：

```text
JSON 客户列表     -> JSON 文件的 item Schema
CSV 晶圆批次表    -> tabular columns
SQLite 数据库     -> registered_format 或后续专用 validator
GDS 版图          -> registered_format，不抽取“版图实体”
Touchstone 文件   -> registered_format，不抽取“网络参数实体”
日志和报告        -> text，不强行拆记录
```

结构化字段契约有三个实际用途：环境 Validator 检查初始数据；工具生成器据此正确解析和生成参数；TaskGen/Verifier 判断工具结果是否有数据库依据。它不代表必须生成增删改查工具。工具能力由 Seed 中的现实能力线索和数据库内容共同决定，例如 GDS 环境应生成层信息分析、几何检查或转换工具，而不是机械地生成 `create_gds/delete_gds`。

## 6. 第三阶段：`ExecutableEnvironmentArtifact`

工具阶段同时接收 `SeedArtifact` 和 `DatabaseEnvironmentArtifact`，这与论文工具生成函数的输入 `(m, D(m))` 一致。

### 6.1 Schema

### 6.2 字段用途

| 字段 | 谁产生 | 谁消费 | 用途 | 为什么不能删除 |
| --- | --- | --- | --- | --- |
| `artifact_type` | 工具阶段 | Loader | 固定为 `executable_environment` | 选择完整环境 Schema |
| `schema_version` | 工具阶段 | Runtime、TaskGen | 完整环境结构版本 | 独立于数据库和工具公开协议升级 |
| `executable_environment_id` | 工具阶段 | TaskGen、rollout、export | 完整可执行环境的稳定 ID | 同一数据库可以产生不同工具版本，不能复用数据库 ID 代替 |
| `database_environment_ref` | 工具阶段 | Loader、Runtime、TaskGen | 引用不带工具环境的精确版本 | 不重复复制数据库 manifest，同时明确引用目标不是完整环境自身 |
| `python_environment` | 工具阶段 | Provisioner、Validator、rollout | 指向可复现的 Python 依赖锁 | 工具代码和专业文件解析包必须在同一环境中运行 |
| `tools` | 工具编译器 | Agent、Runtime、Graph、TaskGen | 唯一公开工具定义 | 对应论文中的工具 Schema 和描述 |
| `tool_bindings` | 工具编译器/Validator | Runtime、CI/Validator | 把公开工具名绑定到 Python 实现和测试文件 | 只有公开 Schema 无法执行，也无法复现论文的工具筛选 |

`tools[]` 严格只有：

```text
name
description
inputSchema
outputSchema
```

`python_environment.format` 当前只允许 `conda_lock`，`path` 指向锁文件，`sha256` 校验锁文件内容。论文和当前目标都使用 Python 工具，所以不再额外保存值恒定的 `runtime: python`。以后如果真正实现另一种执行器，再通过新 schema version 扩展；v1.0 不为尚不存在的 Runtime 预留空字段。

`tool_bindings[]` 不对候选 Agent 暴露。它严格只有 `tool_name/implementation/tests`。`implementation` 固定为 Python 文件的 `path/sha256`；`tests` 固定为一对多测试集文件的 `path/sha256`。不提前规定 reads、writes、参数来源或 Graph 内部结构。

| 嵌套字段 | 消费者 | 作用 |
| --- | --- | --- |
| `tool_bindings[].tool_name` | Loader | 与 `tools[].name` 做一对一关联 |
| `implementation.path` | Runtime、编译检查 | 定位 Python 文件 |
| `implementation.sha256` | Loader、审计 | 防止 Schema 与实际执行代码版本错配 |
| `tests.path` | Validator、CI | 定位该工具的一对多测试集 |
| `tests.sha256` | Loader、审计 | 固定实际用于筛选工具的测试版本 |

`tools[].name` 与 `tool_bindings[].tool_name` 必须构成严格一对一关系，不能有只有 Schema 没有实现的工具，也不能隐藏未公开的可执行 binding。

Python 调用协议是 v1.0 的全局规则，不作为每个工具重复字段保存：

```python
def run(arguments: dict[str, Any], context: ToolContext) -> dict[str, Any]:
    ...
```

每个实现文件都必须导出固定名称 `run`。Runtime 先用 `inputSchema` 校验完整 `arguments` 对象，再从 binding 的 `path` 加载 `run`；返回值必须是 JSON-native，并通过 `outputSchema`。`context` 只暴露本次 rollout 的数据库工作副本和受控文件操作。具体沙箱实现仍可更换，但这个输入输出调用边界不能再由每个生成工具自行发明。

### 6.3 工具保留门禁

按照论文设置工具保留门禁：

```text
implementation 可以编译
每个工具至少有一个测试
测试准确率 > 0.5
实际输入和输出通过公开 Schema
环境至少保留一个有效工具和一个有效测试
```

这里保持论文的保留条件 `accuracy > 0.5`，不在核心契约里偷偷改成另一套实验标准。编译结果、逐例输出、准确率和耗时写入工具阶段旁路验证报告，不复制进最终环境；最终 `tool_bindings` 中出现的工具即表示它已经通过门禁。若以后希望所有测试通过，应作为流水线运行策略升级，而不是给 Artifact 增加冗余字段。

## 7. 第四阶段：`TaskArtifact`

任务合成只接收 `ExecutableEnvironmentArtifact`，再通过其中的 `database_environment_ref` 加载数据库。工具 Schema 不复制进任务。

### 7.1 Schema

```json
{
  "artifact_type": "task",
  "schema_version": "1.0",
  "task_id": "memory_bank_001_task_0001",
  "executable_environment_ref": {
    "id": "memory_bank_exec_001",
    "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  },
  "instruction": "Review the current project context and report the latest recorded decision together with the most recent progress update.",
  "available_tools": [
    "read_memory_document"
  ],
  "answer_schema": {
    "type": "object",
    "properties": {
      "latest_decision": {"type": "string"},
      "latest_progress": {"type": "string"}
    },
    "required": ["latest_decision", "latest_progress"],
    "additionalProperties": false
  },
  "oracle": {
    "reference_solution": {
      "kind": "tool_trace",
      "value": [
        {
          "tool": "read_memory_document",
          "arguments": {"path": "active-context.md"}
        }
      ]
    },
    "ground_truth": {
      "latest_decision": "Use event-driven ingestion.",
      "latest_progress": "The audit migration was validated."
    },
    "verifier": {
      "kind": "rubric",
      "rubric": [
        {
          "criterion_id": "decision_exact",
          "description": "The latest decision matches the database evidence."
        }
      ]
    }
  },
  "five_run_successes": 2
}
```

### 7.2 字段用途

| 字段 | 谁产生 | 谁消费 | Agent 可见 | 用途 |
| --- | --- | --- | --- | --- |
| `artifact_type` | TaskGen | Loader | 否 | 固定为 `task` |
| `schema_version` | TaskGen | rollout、export | 否 | 任务结构版本 |
| `task_id` | TaskGen | rollout、训练、评测 | 否 | 任务稳定主键 |
| `executable_environment_ref` | TaskGen | rollout、Verifier | 否 | 绑定精确的完整环境版本；Loader 再沿引用取得数据库和工具 |
| `instruction` | TaskGen | Candidate Agent | 是 | 最终用户任务，不包含工具名和数据库 Schema |
| `available_tools` | TaskGen | rollout、Candidate Agent | 工具契约由环境解析后可见 | 固定本任务的 action space，不复制工具 Schema |
| `answer_schema` | TaskGen | Candidate Agent、Verifier | 是 | 明确最终答案结构 |
| `oracle.reference_solution` | TaskGen | Verifier、审计 | 否 | 证明任务存在可执行解 |
| `oracle.ground_truth` | 真实执行 | Verifier | 否 | 自动判定答案 |
| `oracle.verifier` | TaskGen | 评测器 | 否 | 支持 rubric 或程序化验证 |
| `five_run_successes` | Five-run | 过滤器、导出 | 否 | 记录固定 5 次独立求解中的成功次数；最终数据集只保留值大于等于 2 的任务 |

`oracle` 和验证字段的最小含义：

| 字段 | 约束 |
| --- | --- |
| `reference_solution.kind` | 只能是 `tool_trace` 或 `python` |
| `reference_solution.value` | Graph 为已实际执行的 `{tool, arguments}[]`；Programmatic 为 solution 文件的 `path/sha256` |
| `ground_truth` | 必须通过任务的 `answer_schema`，由参考解真实执行得到 |
| `verifier.kind` | Graph 为 `rubric`，Programmatic 为 `python` |
| `verifier.rubric` | Graph 的结构化评分项；不在 Programmatic 分支放空数组占位 |
| `verifier.script` | Programmatic verifier 文件的 `path/sha256`；不在 Graph 分支放 `null` 占位 |
| `five_run_successes` | 0 到 5；最终数据集只接收 2 到 5 |

任务不再保存 `episode.database_manifest_sha256`：`executable_environment_ref` 已经精确引用完整环境，完整环境又精确引用数据库产物；数据库文件哈希沿引用链即可得到。每次 rollout 从数据库基线副本开始也是 Runtime 的统一协议，不是任务级配置。

任务不再单独保存 `synthesis_method`。`oracle.reference_solution.kind=tool_trace` 就是 Graph 路径，`kind=python` 就是 Programmatic 路径；再保存一份方法名只会制造不一致。Five-run 次数是全局固定值 5，因此不保存 `attempted_runs/status`，只保存实际成功次数。

### 7.3 Graph 与 Programmatic 的差异

Graph 任务：

```json
{
  "oracle": {
    "reference_solution": {
      "kind": "tool_trace",
      "value": [
        {"tool": "read_memory_document", "arguments": {"path": "active-context.md"}}
      ]
    },
    "verifier": {
      "kind": "rubric",
      "rubric": [
        {"criterion_id": "context_exact", "description": "The answer matches the referenced context."}
      ]
    }
  }
}
```

Programmatic 任务：

```json
{
  "oracle": {
    "reference_solution": {
      "kind": "python",
      "value": {
        "path": "solutions/task_0001.py",
        "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
      }
    },
    "verifier": {
      "kind": "python",
      "script": {
        "path": "verifiers/task_0001.py",
        "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
      }
    }
  }
}
```

这对应论文的两条任务生成路径：图任务保存可执行工具序列和 rubric；程序化任务保存 solution code、ground truth 和 verifier code。

## 8. 各阶段模型究竟看到什么

一次任务 rollout 的 Loader 顺序固定为：

```text
1. 读取 TaskArtifact.executable_environment_ref，并校验完整环境 JSON 哈希；
2. 读取 ExecutableEnvironmentArtifact.database_environment_ref，并校验数据库 JSON 哈希；
3. 校验 database.entries 中每个初始文件，复制 database.root 到独立工作区；
4. 按 python_environment 创建或选择 Python 环境；
5. 校验 tool_bindings 中代码哈希并注册固定 run 函数；
6. 用 available_tools 从 tools 中解析本任务可见的公开 Schema；
7. 把 instruction、answer_schema 和公开工具交给 Candidate Agent；
8. 完成后只把 Agent 回答和工作区最终状态交给 oracle.verifier。
```

这就是“工具阶段合并环境”的实际含义：完整环境通过引用组合 `D + F`，Loader 解析后得到可运行整体；不是把相同数据库字段再复制一遍。

| 模型/程序 | 可以看到 | 不可以看到 |
| --- | --- | --- |
| Research Agent | 完整 Seed | 后续工具、任务和 oracle |
| Environment Generator | 完整 Seed、研究工具 | 未来任务 |
| Tool Generator | 完整 Seed、完整 Database Environment | 未来任务和 oracle |
| Tool Validator | Database Environment、工具实现、测试 | 无需任务 |
| Graph/TaskGen 程序 | 完整 Executable Environment 和数据库 | Candidate Agent rollout |
| 任务生成模型 | 环境 `name/description`、database entry 描述与 content contract、公开工具、候选执行 trace | 实现代码、完整隐藏数据库 dump、未来 verifier 结果 |
| Candidate Agent | instruction、answer_schema、解析后的 available tool schemas、自己的 observations | 数据库 manifest、实现、测试、oracle、five_run_successes |
| Verifier | Task oracle、最终回答、最终数据库状态 | 不需要生成 Prompt |

## 9. 为什么不再使用之前设计的字段

| 旧设计字段 | 处理 | 原因 |
| --- | --- | --- |
| `environment_summary/environment_introduction` | 合并为每阶段的 `name/description` | 两套文本没有独立消费者 |
| `capability_definitions` | 删除 | 与 Seed 的 tool clues 和最终 tools 重复 |
| `data_type_definitions` | 删除 | 与 database entry content contract 和工具 Schema 重复 |
| `constraints_rules` | 收进 `database.rules` | 规则作用于数据库条目，不需要独立顶层命名空间 |
| `initialization` | 删除 | 初始环境就是 `database.root` 指向的目录基线，reset 是统一复制协议 |
| `state_schema` | 删除顶层字段 | JSON 文件由 entry contract 校验，文件树由 manifest 校验，专业文件由注册 validator 校验 |
| `resources` | 合并到 database entries | 环境输入文件和数据库文件本质上是同一执行基底 |
| `provenance` | 改为 `sources + source_refs` | 避免来源信息与每个文件重复 |
| 环境顶层 `internal` | 删除 | 没有确定消费者，不保留空占位 |
| `domain` | 不放单环境契约 | taxonomy 属于环境生态索引，不参与单环境执行 |
