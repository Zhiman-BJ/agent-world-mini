# 半导体场景种子：调研、联合筛选与小样例验证

目标是为后续小型 Agent 环境准备可追溯的种子：明确实体与属性、状态变化、可组合的动作，以及有独立验收条件的任务。一个场景可以涉及多个包；Python 类不自动等于实体，公开 API 也不自动等于最终 Agent 工具。

输入以 [半导体场景分类.md](半导体场景分类.md) 的 L1/L2/L3、实际应用场景为准；代表包和组合关系是待核查的线索。原试点 02.01.01、02.03.03、02.07.01 已完成，覆盖替代、互补、封装/版本冲突三类关系。2026-09-17 按用户要求继续 01、03–08，02 保留既有产物；完整分类清单实际有 160 个 L3，本批范围为 138 个，不能沿用原文“大约60个”作为完成分母。

## 1. 确定一个可闭合的场景边界

从分类表提取场景编号、三级名称、实际应用场景和候选包。合并单元格只补齐上方 L2，不根据包名猜分类。分类文档中只有 L3 列表、缺少具体应用或 L2 的条目，先补齐人工场景清单再处理，不能默默跳过并声称全量完成。

先写一页环境草案：

| 项目 | 必须回答的问题 |
| --- | --- |
| 场景边界 | 要解决哪个重复出现的工程问题？哪些规模、物理机制和外部系统不在本环境内？ |
| 实体/属性 | 哪些对象有身份？有哪些可读/可改字段、单位、范围和对象引用？哪些是输入、配置、中间结果、最终产物？ |
| 状态生命周期 | 如何创建/加载、修改、求解、读取、保存、重置？修改上游后哪些解或指标会过期？ |
| 最小任务链 | 至少两条完整任务；输入已知，动作可执行，目标固定且可独立计算。 |
| 验证条件 | 正常样例成功；故意错误配置失败；修复后成功。哪些断言检查结构，哪些检查物理/数值目标？ |

例如 DEVSIM 的实体是命名的 device/region/contact/model，并不要求为它们找到一个 Python 类；SAX 的模型函数、网表字典和 S 参数也能形成状态空间。后续封装需要给这些对象稳定 ID，并记录版本/依赖关系，而不是只暴露任意 Python 对象。

## 2. 调研实际应用并保存 3–10 个来源

优先官方教程、完整案例、示例代码和实际产品应用说明；至少包含能看清输入、配置、计算与结果的一条链。商业工具案例可以启发工程场景，但不等于相关 Python 包已经实现同样能力。

每条来源记录 `url`、实际跳转 URL、请求状态、页面标题、检查日期、简短内容证据及其对实体/工具/任务的具体启发。失败或需要登录的页面另列，不作为已读成功来源。只查到页面标题而未读到正文时不要推断支持细节。

按场景去重；先保留输入 URL 的原文，不任意删除有意义的路径/查询参数。同一链接可被不同场景引用。文档 `latest`、版本号或源码标签不同的，分别记录；案例页面不能替代包版本证据。

## 3. 找包、固定发布版、建立完整候选池

执行 [Python 包指南](python包搜集整理指南.md) 第 1–3 步：官方身份与文档核查 → 最新稳定发布版 → 标签/提交 → 源码 → 全量静态 API 索引。

- 每个候选包都记录官方仓库、文档、发布来源、实际标签、提交、日期、本地 remote/HEAD/工作区和子模块状态，包括最终排除的包。
- 同名分发先核对身份。例如 `usnistgov/sesame` 是器件求解器，PyPI 的同名 `sesame` 是加密工具，不可混用。
- 已有目录和索引与最新正式发布版匹配时复用，重新解析到内存并逐对象比较。版本变化时使用独立版本目录并重新提取，不覆盖旧源码或只替换哈希。
- 本工作区当前全量目录是 `pypi_outputs/ori_all_funcs/`。旧指南的 `ori_all/` 是历史路径；新流程应显式记录实际路径，不能误用 `package_select_func/`。
- 所有候选包的全量接口合成一个场景候选池。之前的包级 profile 仅可提供参考，不能限制候选范围。

保留源码说明、签名、输入/输出及空值。继承、动态导出、dataclass 生成构造、装饰器、C/C++ 扩展和 Python 公开别名需要单独检查；发现缺口先补来源解析/适配，不编造源 docstring 或伪造方法。

## 4. 以场景为单位联合筛选

先列任务所需能力，再看各包如何承担这些能力，最后确定符号与方法。顺序是：

```text
固定任务与实体状态
  → 所需能力及数据流
  → 各候选包的职责/重叠/版本兼容
  → 选择主实现和必要补充
  → 具体类、函数、方法与桥接入口
  → 小样例暴露缺口后修订
```

每个包选择 `primary`、`complement` 或 `excluded`，写明证据和理由：

| 关系 | 联合选择规则 |
| --- | --- |
| 功能替代 A | 同一实体/物理模型/任务链优先一个主实现；结合官方案例、可本地验证性、公开接口完整度、维护状态和依赖成本决定，不能只比函数数。 |
| 互补 C | 仅保留补齐当前任务缺口的接口；上游输出与下游输入、单位、拓扑/标签/端口和状态所有权必须可描述。 |
| 硬依赖 H / 封装 I | 底层可以安装而不全部暴露；高层负责主动作，底层仅保留确实需要的诊断、构造或独有能力。 |
| 数据传递 D | 列出真实转换函数、输入/输出表示与检查。只知道两个包都能读某格式，不等于标签、单位或物理含义完整互通。 |

补充包即使有独有功能，也需同时满足场景有需求、对象可衔接、版本可共存。不能把任意独有 API 机械拼入。例如 Simphony 0.7.3 要求 `sax < 0.15.0`，不能作为 SAX 0.18.2 的直接可用补充。

具体筛选规则：

- 优先常用公开入口、高层构造/计算/查询和必要诊断；避免让 Agent 重复拼内部实现。
- 同时裁剪类方法；保留必要构造或显式解释对象由何种工厂/继承/运行时生成机制获得。
- 按能力和数据角色去重，不按短名称去重。不同包的 `read` 不一定重复；同包薄包装与原生入口也可能重复。
- 组合能力优于通用细碎辅助，但高层与底层各有明确任务用途时可以并存。
- 构造 → 配置/变换 → 求解 → 观察 → 检查 → 保存/重置主链完整，并允许失败定位和修复。
- 优先本地固定 fixture；外部求解器、GPU、许可证、付费云、下载模型和人工数据输入分别列边界。
- 一个环境参考操作目标 **50–200**。`all_func = function + class_func`，类容器另计；属性/构造沿用来源计数。该数字不是最终 JSON 工具服务器的可调用动作数。
- 不足时检查必要能力是否遗漏，仍不足写例外理由；过多时去冗余、裁长尾或缩小场景。数量不能替代闭环。
- 任务中的包接口必须能追溯到选集；NumPy 数组操作、JSON 存储、运行时构造和 verifier 算术等基础设施单独声明，不能隐藏第二套物理求解器。

profile 保存全部候选包的原始哈希、包级决策、能力分组、显式符号与方法名单、选择原因、桥接和任务配方。`build_joint_scenario_seeds.py` 默认从固定发布源码重新解析并核对全量，再联合筛选，审计每个候选及每个类方法；没有调用 LLM 打分，也不按总分取前 N 项。

能力覆盖检查只能证明显式分组有选中的接口；数据流、物理适用范围和状态生命周期是否完整仍需人工评审与固定样例。基础设施说明不能将未选包接口重新放进任务；只有来源为已选工厂的返回 callable 可以在 `runtime.*` 名字下登记。

## 5. 输出种子和环境设计证据

沿用当前场景快照的外壳，而不修改全局旧契约：

- `environment.basic_info`：`source="deep research"`，场景应用名称、3–10 个研究 URL、采集日期、唯一 index。
- `environment.description/domain/nums`：中文场景边界、分类表原 L1/L2/L3、重算的接口统计。
- `init_ref_tools`：来自全量包索引的原样子集；类只裁方法，不改说明/签名。
- `init_ref_tasks`：完整任务描述的字符串数组。一条任务应包含动作链和验收目标，不把“断言”单独拆成失去上下文的任务。
- `others.basic_info/pypi_package/package_relation/package_metadata`：实际贡献接口的包及原始来源，按相同顺序对齐。
- `others.scenario_design`：实体/属性、能力、数据接口、运行基础设施、完整任务配方、边界及后续封装建议。
- `others.research_sources/joint_selection`：已读取的网页证据、候选包去留、来源与 profile 哈希。

动作 facade 可以在设计里写 `create_device/set_parameter/solve/get_metric/reset` 等概念，但没有代码实现时，不放入参考 API 冒充库函数。后续环境建设还需实现状态存储、工具 JSON 参数、前后置条件、错误返回、输出失效规则、任务隔离与独立 verifier。

## 6. 分层验证与试点门槛

| 层次 | 检查内容 | 能得出的结论 |
| --- | --- | --- |
| 来源 | 官方身份、网页内容、release/tag/commit、重新解析一致 | 来源与版本可追溯 |
| 静态种子 | 精选为原样子集、方法合法、能力覆盖、任务引用、包去留、nums、去重、重生成一致 | 参考种子结构和选择规则正确 |
| 接口运行 | 固定版本安装/import、构造、公开别名、桥接、保存/读取 | 已执行的接口/桥接可用 |
| 任务样例 | 固定输入→失败判据→修复→独立数值/结构断言，多次运行 | 特定样例和容差下的任务链可验证 |
| Agent 环境 | reset/step/state/verifier、权限与任务隔离、状态污染测试 | 后续阶段，本轮不据小样例声称完成 |

校验参考工具仍复用 `schemas/validation/env_seeds.schema.json` 的工具定义。源码缺失的空 description 单列，不补造或放宽全局 Schema；旧包契约不支持当前的中文分类、`deep research` 和字符串任务外壳，不能声称整份旧 Schema 已通过。

最小试点应同时满足：版本和原始来源可重算；可替代包有主次；跨包至少一条真实桥接通过；每场景至少一个固定任务链实跑，错误配置不能只因求解器退出成功而被判完成。失败就记录命令/错误/影响，先修订该场景或将其明确列为阻塞，不启动全量。
