# 工具设计与筛选规范

## 决策

不要让 LLM 根据主题自由编造 Python 工具，再相信它给出的描述。可靠的环境需要
唯一事实来源：一个有类型、可重置的状态模型。只有当工具的实现、模式、描述、
测试、观测到的效果以及图中的边都与该状态模型一致时，工具才能通过验收。

本项目的实现顺序如下：

```text
挖掘得到的快照 -> 状态契约 -> 操作意图 -> 可执行工具
-> 独立测试 -> 筛选 -> 数据流图 -> 可执行链
-> 任务表述
```

自然语言工具描述和任务表述被有意安排为靠后的产物。它们描述的是已经运行过的
代码；绝不能把它们作为代码预期行为的权威依据。

## 初始原型中发现的问题

初始版 `ToolDesigner` 保留了五个固定名称，只允许 LLM 替换它们的描述。
`LocalToolRuntime` 包含相应的固定实现。本节记录促使我们采用当前数据驱动工具
生成器和共享运行时的问题。

实际问题如下：

1. `list_operational_entities`、`filter_entities` 和 `compare_entities`
   是通用数据浏览操作，而不是从研究所得业务状态中派生的领域操作。
2. 工具模式没有编译到运行时行为中。生成的输入或输出字段可能出现在文档里，
   运行时却会忽略它。
3. `reads`、`produces` 和 `requires_tools` 只是粗粒度字符串。它们无法证明
   某个特定输出字段能满足后续的某个特定输入。
4. 没有工具级生成测试用例、独立测试代理，也没有状态转换或重置测试。
5. 运行时是只读的。对于完全由公开信息查询构成的世界，这是合理的，但不能将其
   描述为有状态的业务环境。命令必须有建模后的本地状态和有据可查的工作流支持，
   不能仅仅为了构造更长的链而凭空编造。
6. 现有项目测试只检查图和任务的形状，并不检验工具契约、代码及其声明的输出
   是否一致。

## 文献的实际要求

Agent-World 会同时生成一个候选 Python 函数和一对多的单元测试集，然后只保留
能够编译且测试准确率高于 0.5 的候选项。它并未声称单靠工具描述即可证明工具质量。
[Agent-World](https://arxiv.org/abs/2604.18292)

EnvFactory 明确规定了这种耦合关系：元数据包含工具和模式；数据库模型提供实体、
关系和可变状态；代码实现工具接口；独立的 Test Agent 会检查元数据与接口的一致性、
导入/执行、预期行为和数据库状态转换，然后返回错误报告以供修订。
[EnvFactory](https://arxiv.org/abs/2605.18703)

AWM 提供了另一项互补约束：它只在任务需要时构建数据库表，采用 SQLite 支撑的状态，
公开 Python 工具并验证执行。不要在正确性得到保证前照搬它的规模：其自身分析仍
报告了实现缺陷。[AWM](https://arxiv.org/abs/2602.10090)

成熟的评估环境进一步印证了同一个要点。AppWorld 评估最终状态和非预期的连带变更；
ToolSandbox 检验隐式状态依赖；tau-bench 比较数据库的终态，而不是某个指定的
工具调用字符串。参见 [AppWorld](https://arxiv.org/abs/2407.18901)、
[ToolSandbox](https://arxiv.org/abs/2408.04682) 和
[$tau$-bench](https://arxiv.org/abs/2406.12045)。

## 目标产物

### 1. 状态契约

Research Agent 必须在工具设计之前输出 `StateContract`。它是本地快照的机器可读
摘要，而不是以散文形式编写的数据库概要。

```text
entities: 实体名称、主键、有类型字段、来源溯源信息
relations: 源实体.字段 -> 目标实体.主键、基数
indexes: 实际可以搜索、排序、分组或连接的字段
invariants: 唯一性、允许值、数值范围、引用完整性
state_classes: immutable_source | local_overlay | derived_view
workflow_evidence: 有来源依据的业务操作及其允许的转换
```

`immutable_source` 是挖掘得到的事实快照。`local_overlay` 是可选的会话状态，
例如草稿、预订请求或问题状态。它必须与来源事实分开存放，能够在每次推演时重置，
且只有在公开文档支持底层工作流时才能引入。这样可以避免悄然改写真实网页数据，
或虚构没有依据的操作。

### 2. 先定义操作意图，再编写代码

LLM 只能以受约束的 `ToolIntent` 对象提出操作。它必须引用所依赖的状态字段和
工作流证据。

```json
{
  "name": "search_bicycle_stations",
  "kind": "query",
  "target_entity": "station",
  "inputs": [{"name": "query", "type": "string", "source": "user"}],
  "outputs": [{"name": "stations", "type": "StationSummary[]"}],
  "read_paths": ["station.name", "station.city"],
  "write_paths": [],
  "preconditions": [],
  "effects": [],
  "evidence_ids": ["source-17"],
  "rationale": "Supports station discovery using fields present in the snapshot."
}
```

第一版实现允许的 `kind` 值如下：

| 类型 | 用途 | 准入规则 |
| --- | --- | --- |
| `query` | 搜索/筛选真实实体集合 | 至少一个已有数据的字段被编入索引或可搜索 |
| `lookup` | 按规范 ID 获取记录 | 主键和记录类型均存在 |
| `relation` | 遍历显式实体关系 | 关系已物化且满足引用完整性 |
| `aggregate` | 计数、分组、排序或汇总 | 所有字段和聚合操作的类型均有效，且数据具有有意义的差异 |
| `create` | 创建覆盖层记录 | 覆盖层模式和有据可查的工作流均存在 |
| `transition` | 更改本地覆盖层状态 | 允许的转换及其前置条件均已明确 |
| `delete` | 删除/取消覆盖层记录 | 所有权、转换和重置语义均已明确 |

不能仅仅因为 `compare` 或 `recommend` 听起来像业务操作，就允许这类意图。
比较操作需要共有的有类型字段；推荐操作需要调用方提供明确的确定性标准，或有据
可查的策略。否则，它只是伪装成工具、无法验证的 LLM 判断。

### 3. 编译意图，不要在运行时让 LLM 解释意图

在这个迷你复现项目中，应使用一个可信的共享编译器，将 `ToolIntent` 编译为在
可重置、有类型的内存存储上运行的 Python 函数。搜索、关系遍历、聚合和覆盖层状态
转换都由编译器而非 LLM 实现。这样可以让每次推演的语义完全一致，也无需为每个
主题分别编写服务实现。

后续可以允许 LLM 生成 Python 实现，以更贴近 Agent-World，但只能在沙箱中进行，
并且必须先通过下文所述的同一套静态绑定和测试。以受约束的操作 DSL 起步，既能减少
潜在故障面，又能让每个研究主题拥有不同且有数据依据的工具集。

### 4. 从代码派生面向代理的契约

编译后，输出包含以下内容的 `ToolSpec`：

```text
name, description, kind
input JSON Schema, output JSON Schema
input sources: user | constant | tool.output path
reads, writes, preconditions, effects, error contract
determinism and pagination/sort policy
provenance/evidence IDs
implementation ID and test IDs
```

根据该模式生成描述，并测试其完整性。描述应说明工具的作用、必需输入、返回值以及
任何状态变更。不得泄露隐藏的任务答案，也不得声称意图中不存在的能力。

## 候选项生成协议

1. 从规范化研究包中推断并验证 `StateContract`。拒绝格式错误的记录，并将每个
   关系标记为已验证或不存在。
2. 只向 LLM 提供契约、来源摘录和允许使用的意图词汇。要求其给出数量适中的
   候选集，例如小型环境提供 3--12 个工具，而不是固定的通用工具列表。
3. 对声明的每个表、字段、关系、转换和证据 ID 进行静态绑定。任何无法绑定的引用
   都应在生成代码之前被拒绝。
4. 将通过验收的意图编译为可执行函数，并派生模式。
5. 使用独立的测试生成步骤，根据契约和具体的夹具 ID 创建测试。它不能直接复用
   候选工具的预期输出，而必须从数据库重新计算结果。
6. 在干净快照上执行测试，以结构化形式报告失败，在固定预算内修订意图/代码并
   重复这一过程。
7. 只有工具通过测试后，才能构建工具图并采样链。

LLM 在第 2 和第 5 步中可以发挥作用：识别领域语义并提出覆盖方案。它不应同时
成为同一工具唯一的执行器、编译器、预期结果提供者和裁判。

## 工具筛选协议

以下所有关卡都必须通过。数值评分无法弥补正确性关卡未通过的问题。

| 关卡 | 测试 | 拒绝条件 |
| --- | --- | --- |
| 静态落地 | 所有实体、字段、关系、证据、读写路径和类型均绑定到 `StateContract` | 任何名称、字段或业务规则是虚构的 |
| 可编译性 | 生成的模块可以导入，工具可以注册 | 导入、模式或注册失败 |
| 契约一致性 | 有效调用符合输出模式；无效调用返回已声明错误 | 运行时接受或返回文档未说明的结构 |
| 行为测试 | 典型、空、边界、无效输入和未找到场景 | 任何确定性预期结果不一致 |
| 不变量 | 读取调用不改变状态；写入调用保持外键、允许的转换和幂等规则 | 状态违反不变量或无法重置 |
| 数据实用性 | 查询结果不是退化结果；聚合操作使用有效的有类型字段，且至少有两个有意义的值 | 工具总是返回相同的无意义值或空数据 |
| 图实用性 | 至少有一条类型兼容的输入/输出路径，并且能够执行一条链 | 工具不可达、无后继，或存在无法满足的必需输入 |
| 冗余性 | 将规范签名和行为与已保留工具进行比较 | 工具只是别名，没有新增操作、作用范围或效果 |
| 集成 | 在全新状态下，采样链使用真实输出满足下游输入 | 链只有注入隐藏参数后才能运行 |

对于小型演示，应要求确定性测试 100% 通过，而不是采用 Agent-World 的
`Acc > 0.5` 准入阈值。后者是面向大规模场景的务实筛选标准；在当前规模下，修复
一个在已知确定性测试中失败的工具成本很低，不应保留这种工具。

与 Agent-World 一样，环境本身只需拥有至少一个有效工具和一个有效测试即可保留，
但通常还应要求至少有一条非平凡的可执行链。只读环境可以通过验收；不需要为了让
环境显得更难而虚构变更操作。

## 图构建必须使用有类型的数据流

将当前仅依赖产物名称的图替换为二部图：

```text
Tool -> OutputField/StateEffect -> InputField/Precondition -> Tool
```

每条边都必须基于下列理由之一：

- `strong`：某个输出字段能够准确提供下游所需输入；
- `weak`：通过某个关系或查询可以派生所需值，但也可能存在其他来源；
- `independent`：工具只接受用户输入/常量输入，因此可作为有效的新起点。

输入必须声明其来源。只有当每个必需输入都是用户可提供值、有类型的先前输出或安全
常量时，图游走才可执行。这样可以避免当前的问题：两个工具都提到了
`operational_entities`，一条链因而看似有效，但第二次调用实际上并未使用第一次
调用的结果作为参数。

如 EnvFactory 所做的那样，语义匹配和 LLM 优化可以提出 `weak` 边，但运行时必须
通过执行具体绑定来证明每条 `strong` 边。不要将随机游走用作依赖正确性的证据。

## 进一步实验之前需要添加的测试

1. `test_intent_rejects_unknown_field`：LLM 不得按状态契约中不存在的字段进行
   筛选或排序。
2. `test_tool_schema_matches_runtime`：每个有效示例调用都符合所声明的输出模式；
   每个无效示例都会产生所声明的错误。
3. `test_read_tool_preserves_snapshot`：查询/查找操作不能改变状态。
4. `test_transition_respects_preconditions_and_reset`：允许的覆盖层状态变更能够
   成功，无效转换会失败，重置会恢复快照。
5. `test_graph_edge_has_executable_binding`：每条强边都有一个下游工具可以接受的
   具体上游值。
6. `test_generated_chain_runs_without_hidden_values`：实例化所有已声明的用户输入，
   然后在没有仅预期结果提供者可见参数的情况下执行整条链。
7. `test_duplicate_tool_is_pruned`：语义相同的工具不会同时对外公开。

## 具体实现顺序

1. 在 `agent_world_mini/schemas/models.py` 中添加 `StateContract`、
   `ToolIntent`、`ToolTestCase` 以及有类型的输入/输出绑定。
2. 将 `agent_world_mini/env_gen/tool_gen/designer.py` 中固定的回退逻辑替换为
   配置生成、静态绑定和受约束的编译器。在内部保留通用操作；只有数据支持时，
   才对外公开使用领域名称的工具。
3. 将按名称分支的运行时替换为状态后端和已编译工具注册表。添加快照/重置支持。
4. 添加筛选/测试/修订循环，并持久化 `tool_validation.json` 产物，其中包含每个
   候选项、拒绝原因、测试轨迹和保留的契约。
5. 围绕有类型的参数绑定重建 `agent_world_mini/task_gen/dag_form/graph.py`，
   并在任务合成之前执行每条采样链。
6. 保留现有的任务参考执行和五次运行测试，但只有在通过工具级验证后才运行它们。

此顺序有意先提高有效性，再追求更长的链或更多任务。对于当前的自行车共享数据，
最终可能只得到一组规模较小、以读取为主的工具，例如搜索站点、获取站点、列出一条
已证实的关联记录，以及计算一个有证据支撑的聚合值。如果挖掘的数据不支持真实的
事务型工作流，这就是正确结果。
