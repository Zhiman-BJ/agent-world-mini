# MCP 种子筛选与评分 v1

适用对象：`seed_gen/data/smithery_1000_v1_0902.json` 的环境种子 v1.1，以及后续 `seed_gen/catalog.py` 生成的同类数据。
目标：选择能合成**实体与属性明确、工具可组合、业务流程完整、结果可验证**的环境。本文的评分是来源材料支持的合成潜力评估，运行验收单独进行。

## 1. 两个阶段分别处理

1. **采集时限量**：每个服务最多保留 100 个有效参考工具；记录截取方法，保证工具数量和 `environment.nums` 一致。
2. **采集后筛选**：先审计材料，再按业务含义评分。没有工具材料的种子先补采；不能把“未采到”与“不适合”混为一谈。

服务级 `use_count` 仅用于安排采集/复核顺序；工具数只作为成本和材料规模指标。它们均不直接进入合成适用性总分。

## 2. 下次采集的工具上限

`catalog.py` 的 `_seed_from_detail()` 先沿用已有规则过滤缺名字、缺有效描述的工具，再调用 `select_reference_tools()`：

| 条件 | 保留策略 |
| --- | --- |
| 有效工具数 ≤ 100 | 全部保留，维持原顺序 |
| 超限，且每个工具均有合法的同一个 `useCount` 字段 | 按工具级使用次数降序保留前 100 个；并列时保留来源顺序 |
| `useCount` 不满足上述条件，但每个工具均有合法的 `use_count` | 用此字段采用同样策略 |
| 两个字段均不完整、没有或非法 | 按来源顺序保留前 100 个 |

合法次数为非负有限数值，排除布尔值与字符串。不把缺失次数补成 0，不混用两个来源字段，不拿服务级 `use_count` 当作工具级次数。
当前种子中的工具都没有使用次数字段，因此本次离线预览使用来源顺序。这里没有确认实时 API 是否支持工具级统计；未来只有实际返回此字段时才启用排序，也不为查使用量逐工具发额外请求。

工具限额为**生成的参考工具集合**上限。详情接口仍可能一次返回完整工具列表；该规则不承诺减少详情响应字节数。它作用于 `prepare_smithery_catalog()` 的种子导出路径；历史主题发现路径 `discover_smithery_themes()` 不生成本格式，未改动。

新增 `others.tool_selection` 审计信息（自定义 key 使用 snake_case）：

```json
{
  "limit": 100,
  "eligible_count": 132,
  "retained_count": 100,
  "removed_count": 32,
  "strategy": "source_order",
  "ranking_field": null,
  "received_count": 133,
  "invalid_count": 1
}
```

`received_count` 是种子投影函数接收到的工具列表长度（详情读取器可能已过滤缺名字项），`invalid_count` 是投影阶段排除的项数。
`removed_count` 仅表示有效工具因限额被去掉的数量。`strategy` 为 `all/source_order/tool_usage_desc`。
`environment.nums.function` 和 `all_func` 按保留后的数量计算，`class/class_func` 仍为 0。
参考工具本身沿用现有 `name/type/module/description/input/output` 投影，不为了评分修改参数、补造输出或静默去重。

```powershell
# 下次采集命令示例，本次未执行网络爬取；建议另存新快照
python -m seed_gen.catalog --source seed_gen/data/smithery_servers.json --output seed_gen/data/smithery_next_v11.json --limit 1000 --max-tools 100
```

`--max-tools` 可指定 1–100，默认 100；不能用 0 或更大的值绕过上限。当前历史快照保留原样。
100 是本次 Smithery 采集策略，不作为通用种子 Schema 的 `maxItems` 限制，避免误伤其他来源及历史快照。

## 3. 初筛：材料审计和分流

当前实际统计见 `reports/smithery_seed_screening_20260911/analysis.md`；机器可读结果在同目录 `analysis.json`。

| 检查 | 分流或处理 | 不应推导的结论 |
| --- | --- | --- |
| 无有效参考工具 | `needs_tool_evidence`：补采详情、检查来源 | 不等于服务本身无工具或低质量 |
| 1–4 个工具 | `small_toolset_review`：复核工具是否含多操作、是否适合专项环境 | 不自动淘汰，小工具集也可能闭环 |
| 5 个及以上 | `semantic_review`：进入语义复核 | 不自动合格，也不按数量加分 |
| 超过 100 个 | 模拟限额后再评分，标记 `truncated_preview` | 原集合高分不能直接继承到截取集合 |
| 空 `output` | 待补输出信息；可验证性需要读回/公式等其他证据 | 不等于无返回值或一定不可验证 |
| 空 `input` | 可为合法无参工具 | 不判成缺失参数 |
| 重名工具 | 标记，复核是否版本/语义冲突 | 不静默删工具 |
| 不同服务工具定义完全相同 | 作为去重线索，复核来源和版本 | 不据此断定环境完全相同 |
| 未提供任务 | 评估可合成任务空间 | 不因 `init_ref_tasks=[]` 扣分 |

只有来源不可追溯、材料无法解析、已知与目标不匹配且证据充分时，才确定拒绝。鉴权、实时 API、外部系统依赖需要列出拟本地化的边界；它们本身不构成一票否决。

**现有材料的边界**：`_reference_tool()` 只提取输入/输出 Schema 的 `properties`，不会保留根级 `required/oneOf/$defs` 或数组/标量输出的完整定义。因此不能通过当前种子还原所有必填关系，也不能把空输出全部归咎于上游网站。本轮保留现有契约和投影逻辑；后续需要输出证据时，应回到原始详情/官方接口定义补充，而不是手填旧种子。

## 4. 合成适用性评分：六个维度，100 分

每项 0–5 分，分数越高越有利；总分 `S = Σ(weight × score / 5)`。
**0 表示有证据确认不具备，未知使用 null，不按 0 处理，也不把剩余权重重新归一化。** 有未知维度时总分为 null，同时保留已知项及待补证据。
批量脚本不会用工具名关键词给语义维度自动打分。当前提供 8 个有依据的完整静态评分样例，其余记录 `suitability_score=null`。

| 维度 / key | 权重 | 核心判据 | 主要依据 |
| --- | ---: | --- | --- |
| 常见性与迁移性 `commonness` | 10 | 是否围绕常见对象和任务，可迁移到多种业务 | 环境描述、对象及场景；平台知名度不直接计分 |
| 实体与属性模型 `entity_model` | 20 | 实体种类、属性可定义程度、主键/引用/关系、约束 | 参数与输出、描述中明确的对象；参数名数不等于实体数 |
| 工具操作覆盖 `operation_coverage` | 15 | 查询、写入、关系管理、状态迁移、约束检查等有效操作类别 | 实际工具语义、参数和副作用；同类查询接口不重复奖励 |
| 环境业务闭环 `workflow_closure` | 20 | 核心业务是否从发现对象到执行、结果读取、后续处理完整 | “实体 × 操作 × 前后置条件”矩阵、外部依赖边界 |
| 可验证性 `verifiability` | 20 | 是否能用状态、结构化数据、独立公式或不变量判断正确性 | 读回接口、输出结构、错误条件、可冻结时间/数据、独立判定方式 |
| 多步任务组合性 `task_composability` | 15 | 是否存在真实参数/状态依赖，以及有约束的分支和跨实体任务 | 具体调用链、每条边的依赖证据、最终断言 |

### 4.1 分数锚点

| 分值 | 常见性 | 实体与属性 | 操作覆盖 |
| ---: | --- | --- | --- |
| 0 | 与目标用户/业务明确无关 | 无业务实体，仅标量或文本变换 | 没有目标场景的有效操作 |
| 1 | 极窄且难迁移的单用途场景 | 单一对象，属性及标识很弱 | 单一能力或薄封装 |
| 2 | 较窄专业场景 | 1–2 类对象，关联很弱 | 多个查询或计算接口，操作类别少 |
| 3 | 一类常见业务，迁移范围有限 | 约 3 类可辨识对象，属性/关系仍缺较多 | 查询加部分写入/关系操作 |
| 4 | 通用基础场景，但需指定具体业务 | 约 3–5 类清晰对象，有属性与引用线索 | 多类查询、写入、关联或状态操作，少量关键缺口 |
| 5 | 高频生活/业务对象，跨场景复用明确 | 约 5 类以上有意义对象，多属性与多关系可落地 | 覆盖目标领域需要的完整操作谱系，包含边界/异常处理 |

实体数量是校准参考，不是硬阈值；日历等 3 类实体也可以高质量。不能通过拆分字段或增加分页接口抬高得分。

| 分值 | 业务闭环 | 可验证性（静态潜力） | 多步任务 |
| ---: | --- | --- | --- |
| 0 | 与预期业务无完整子流程 | 正确性仅依赖主观偏好，无法提出客观判据 | 功能孤立且无法组成任务 |
| 1 | 单函数独立有效，业务场景需另造 | 仅成功标志或模糊自然语言结果 | 串接主要是人为拼接 |
| 2 | 有局部功能，主流程缺多处关键动作 | 可拟定判据，但输出/实时依赖等证据严重不足 | 短计算链或独立并行查询，依赖较弱 |
| 3 | 一条局部主链可闭环，其余有明显断点 | 有明确读回入口或独立公式，尚缺正式输出/状态规则 | 至少一条 3 步左右真实数据/状态依赖链 |
| 4 | 主链及部分后续处理完整，少量约束需补 | 主要结果有结构化读回和可执行断言设计，依赖可明确隔离 | 有多种 4–6 步链或跨实体约束，分支可设计 |
| 5 | 目标边界清晰，主链、失败/取消及关键不变量均有明确规则 | 材料足以具体定义状态/输出、不变量、失败断言和确定性重放方案 | 多种自然任务族、依赖链和条件分支，难以用单个万能调用替代 |

可验证性 5 分也仅表示材料充分，**不代表已实现或已执行成功**。只读环境也能凭冻结数据和独立算法取得高验证分；数学工具在验证方面可得分，但在实体维度可能为 0。
只凭名字不能判定读写，例如预订服务 `get_quote` 的描述明确说会创建 15 分钟锁定，属于有状态副作用的操作。

### 4.2 推荐门槛

初版门槛用于排复核优先级，尚未用实际生成成功率校准：

- `S ≥ 80`：优先候选；其中实体、业务闭环、可验证性、多步任务均应至少 3 分。
- `65 ≤ S < 80`：保留，先限定子场景或补关键证据，再试做。
- `S < 65`：不优先作为通用实体型环境；查询、计算等有明确价值的种子进入专项池，不直接删除。
- 任一核心维度未知：进入补证池，不用低分冒充已判定不适合。
- 高分且验证分仅 3：可先补证/做一个小规模本地环境，不应直接批量生成。

总分不能掩盖短板：90 分但不能提出客观任务终态，不进入生成队列。首次试做建议优先比较 Airtable、日历和 Linear 三类；实体多、调用多不是优先于边界清晰和验证材料的理由。
每个高分候选至少写出一条端到端链和相应断言，确保“闭环/组合性”不是空泛印象。

## 5. 审核记录与任务证据

人工评分样例保存在 `seed_gen/data/mcp_seed_review_examples_v1.json`。每项包含：

- `name`：对应真实 `environment.basic_info.name`；报告补上 `global_id`、来源 URL、原始及保留工具数。
- `dimensions`：六项分数和逐项理由。
- `entity_evidence/evidence_tools`：实体线索和真实工具名。
- `proposed_task_chain/chain_dependencies`：拟合成调用链及依赖依据；未知的返回键必须列入待补项。
- `proposed_assertion/missing_evidence/recommendation`：客观终态判据、缺口及处置建议。

例如预订链 `search_properties → check_availability → get_quote → create_reservation → confirm_reservation → get_reservation`：
`property_id` 来自房源选择，`quote_id/hold_id` 的来源在预订工具参数说明中指向报价工具，之后按 `reservation_id` 确认及查询。
最终应检查预订对象、日期、人数和状态，以及占用/锁释放不变量。当前输出为空，以上是**有来源依据的合成方案**，不是现有执行轨迹。

不能只用“前一步和后一步都有 id”连边；必须明确实体类型、具体字段、转换、作用域和前置条件。
不能为了增加步数强制调用可省略的查询；需要初始状态、隐藏信息或约束使这些调用有实际必要。
不能把 `success=true`、文本出现“完成”、工具返回的自评作为最终验证。

## 6. 生成后的最终准入

静态高分后，先用一个小环境验证以下内容，再逐步扩展：

1. 固定初始实体、时钟、随机源和外部资料，明确允许读写的状态；相同初始条件可复现。
2. 为每个保留动作实现输入/输出、前后置条件和错误语义；缺少关键读回时先补齐正式工具设计。
3. 任务从独立初始状态执行，有真实数据或状态依赖；记录所有输入、结果和状态变化。
4. 验证器用独立读回、最终状态或参考计算检查目标条件及不变量，并确认无关对象未被改变。
5. 验证失败分支、错误参数、不满足前置条件及同初始状态重放；“有输出 Schema”不能替代这些检查。

可记录的后续校准指标：生成成功率、验证器判定覆盖率、从重置状态的重放通过率、独立任务族数量、有效依赖边比例、合成时必须新增的实体/工具比例。
如果一个种子必须大量新增来源中不存在的工具才能闭环，应降低来源适配评价，而不是把新增能力算成原种子的优点。

## 7. 当前数据的分析与复现

当前快照有 975 条环境、10,592 个工具；550 条没有工具，126 条有 1–4 个，287 条有 5–100 个，12 条超限。
