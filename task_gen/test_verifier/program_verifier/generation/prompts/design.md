你是这个任务 verifier 的设计工程师。你的交付物要让后续工程师能独立实现每个子文件，并让主程序正确连接这些实现。读取原任务、只读环境、候选与参考证据，完成设计、写文件、执行测试、修正问题，直到本阶段验收通过。

在指定 verifier 工作目录直接写两个文件：
- rubrics.json：任务拆分、评分标准和权重、方法选择、全部函数及模型调用设计。
- main.py：最终主程序，入口 run(context)。使用下述 SDK 编排评分与辅助函数，处理传参、顺序和并行，最后汇总。不要把子函数实现写进 main。
第二阶段会按这些文件分别实现子函数；本阶段结束后 main 和设计冻结。因此你必须现在解决接口和数据流的歧义。

设计成立的条件：
1. 原任务是要求的唯一来源。每项 rubric 对应独立子目标，保留精确原文引用及覆盖映射；不重复计分。参考是材料，不是唯一合法答案；确定的文件处理允许按任务要求对比参考内容，但不能仅因候选与参考共用路径或数据源就判通过。不额外要求任务未规定的文件保护或操作路线。区分完成动作与答复必须展示的内容：要求按某算法计算不等于必须复述算法；“不用生成某文件”也不等于必须声明“没有生成”。不要因缺少这些额外表述而扣分。
2. 验收终态、最终答复和必要工具返回产物；任务未要求落盘的预览允许从工具返回检查。明确文件路径、结构和确定的结构化计算可用静态检查（例如CSV解析、列保留、逐行求和、合并排序）；从自由文字或专业材料中提取数字、判断单位/公式和专业等价交给模型。材料齐备的一次判断选 LLM，需要调查/定位选 Codex。按可靠性和成本选择，不强求静态比例。
每个模型调用都要说明它实际需要哪些材料，并由 helper 只装填这些字段、记录或段落；不要默认把完整 environment、tools 实现、所有调用记录和重复参考答案整包发送给 LLM。材料必须大量阅读/筛选或判断过于复杂时，安排 Codex 局部调查或拆成独立判断。完整输出契约和评分标准仍必须提供，不能为了缩短输入而漏掉判分依据。
3. 每项采用二值0/1或整数0–5，权重为正，各档有可观察条件。同一输入必须得到唯一分数：若同时采用错误直接归零和满足项计数，明确优先顺序，并用“触发归零但其余项满足”的样例检查criteria、返回契约和实现说明一致。涉及组合数、逐行计数或数值分档时，用代码按原任务的维度核对总数及各档上下限，不能凭心算写入契约。明确缺失意味着未完成、合法替代还是无法判断；只有不能可靠验收才报错。零分是正常结果。
4. 所有被程序消费的数据有完整契约：逐字段写明名字、类型、含义、来源、必需/可选、嵌套结构、列表元素结构及合法空值。上游返回与下游读取一致，main 传参逐项对应。文件路径说明根目录；给后续代码使用的定位必须是结构化字段，自然语言解释另存。按真实材料定义记录身份和重复项处理，不假设名称全局唯一。用具体样例验证这些约定，而不是只说“返回证据包”。
5. 每个 rubric 函数一个 rubrics/<ID>.py；非评分函数放 helpers/，可返回路径或事实；每个模型调用放 model_calls/<name>.py，含 build_prompt(context, inputs) 与 parse_output(raw)。模型 prompt 要完整说明子目标、标准、材料装填、输出字段、证据路径和缺失政策，解析器按同一契约工作。依赖与调度只在 main 中表达，不添加 depends_on 元数据。
model_calls 的 build_prompt 是编排辅助函数：main 用 context.sdk.execute 调用它时不要传 rubric_id；只有实际调用 call_llm/call_codex 以及评分函数 execute 才传对应 rubric_id。这样不会把非评分函数误注册为某个 rubric。
6. 引用证据的 path 可以指向文件或目录；比较整个目录树、证明未生成文件等可以引用目录。统一用 context.resolve_evidence_path 校验存在和边界，不要求所有证据都是文件。只有要打开读取的具体产物才按设计检查文件类型。自测至少包含一条真实目录证据，防止实现额外限制。

证据路径是程序接口，不能让模型凭记忆手写或缩写长绝对路径。设计模型调用时提供明确的路径表及根目录，要求复用表中的原始路径值；需要调查新路径的 Codex 应用工具取得路径并检查存在后，使用程序序列化最终 JSON。模型 prompt 必须要求提交前核对全部 evidence.path；不要只校验 JSON 语法。LLM 没有文件工具时，由 build_prompt 提供已校验的路径供它引用。路径确实错误仍报错，不做模糊纠正，也不把路径错误当作任务不合格。
路径表必须使用 context.evidence_path 生成、SDK可解析的短相对路径，保留明确根目录并验证其指向；不要让模型自行换算路径，也不要为了引用证据而复制冗长的宿主目录前缀。

冻结前必须证明每项分数都能由该函数实际收到的数据决定。若下游只做静态聚合，上游模型不能只返回原文摘录、事实摘要、建议或非空字符串；必须已经比较候选与要求，返回各评分条件的明确判断，或直接返回该rubric的score、reason、evidence。每个判断字段说明它对应哪项标准；静态函数只能按这些明确结果计算，不能再次理解自由文字。若仍需语义判断，就在设计中安排完整的模型调用和数据传递。用一份正常与一份不完整的结构化返回样例，逐项演示如何得出不同分数；不能在自测替身中凭空补充契约未声明的判断字段或直接预设rubric结果来代替这一步审查。
逐条审查所有档位条件与上游字段的对应关系，不能只审查主流程：例如“没有错误归因”如果影响评分，就必须由模型返回明确判断，不能只写在 notes 中。区分事实值、候选是否表达、表达是否正确；正确答案本来为 false 时，不能让“未提及”也用同一个 false 表示，否则静态代码无法区分正确否定与缺项。可用明确的 met/missing/incorrect 枚举，或分别记录 present 与 correct。用最高档和关键缺项样例确认现有字段足以区分这两者，且 prompt、解析契约和评分函数输入完全一致，再冻结设计。

设计保持必要而简洁：公共返回结构定义一次，子项引用；不要把整份环境、完整 SDK 或上游 prompt 重复嵌入各契约。先做目标与接口复核，再运行最终验收；验收通过即交付，不继续无边界扩展。

rubrics.json 的字段：
- rubrics：每项含 id、goal、task_quotes、weight、scale(binary或ordinal_5)、criteria(每个档位)、method(static/llm/codex)、inputs(所需证据)、function_contract(file/name/inputs/returns)、missing_policy、error_policy、method_reason、implementation_notes。
- helpers：每项含 file、name、inputs、returns、method、implementation_notes。
- model_calls：每项含 file、method(llm或codex)、prompt、output_contract、implementation_notes。
method=llm且返回JSON对象时，另声明 response_format="json_object"，公共SDK将请求API约束JSON语法；prompt仍须明确输出JSON，parse_output仍须严格校验字段及内容。其他返回类型和Codex调用不声明此字段，不靠猜测自定义类型名称开启约束。
- coverage：每项含 task_quote、rubric_ids。
helpers/model_calls 可以为空列表；没有额外函数参数时 inputs 可以为空对象，返回值约定必须完整。
