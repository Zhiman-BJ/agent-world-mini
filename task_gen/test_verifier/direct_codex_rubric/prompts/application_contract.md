沿用原始 task_eval_verifier 的调查流程：先阅读 request，再独立调查，将逐项证据和结论记录在 scratch/investigation.md，然后按本方法独立生成且固定的 rubric 评分。不提供预生成静态工具。

## 生成及冻结前复查：逐层说明必要性

本节是 Direct 专属设计要求，补充共同设计说明。生成和最终复查时，rubrics.json 中每个 rubric、subcriteria 中每个子项及更深层子项，都必须明确提供：
- required_for_pass：布尔值，表示满足该项的 pass_condition 是否是整体通过的必要条件。
- necessity_reason：根据该项 task_quotes 中的任务原文，解释为何必要或非必要；不能只写“重要”，也不能依候选表现或分数决定。
- pass_condition：可核实的满足条件，说明必须交付的内容、适用指标、容差或允许的等价实现；开放式目标按任务要求的实质内容判断，不预设唯一方案或唯一结论。
- veto_condition：什么已证实的缺失或实质错误会使本项必要条件不满足；非必要项明确说明本项局部不足本身不触发否决。

子项用 subcriteria 对象数组表达，每项有稳定 id、goal、task_quotes 及上述字段；存在多个独立检查要求时须逐项列明，不能把子项及其必要性只藏在长段落或评分档位里。没有子项则用空数组。已有 subcriteria 应规范成该结构，不重复计分。

所有层级的 id 必须是非空字符串且全包唯一。宿主在生成自测、复验及冻结前递归校验上述结构：required_for_pass 必须是真正的布尔值，goal、necessity_reason、pass_condition 和 veto_condition 必须是非空字符串，task_quotes 必须逐条精确引用原任务，subcriteria 必须是数组。可调用 task_gen.test_verifier.direct_codex_rubric.contracts.validate_package(root, task_text) 自测；缺字段、类型错误、重复 ID 或子项引用不属于任务原文时须修正后才能冻结。结构校验不代替必要性及条件合理性的语义复查。

必要性与分数、权重分开：必要项仍可按固定档位获得部分分数，但未满足其 pass_condition 时，主 Codex 必须判整体 fail，其他高分不能补偿。必要子项独立生效，父项的非必要标记或综合得分不能取消它；父项必要也不意味着所有子项都必须满分，须分别写清满足边界。非必要项得满分不能自动证明整体通过。

不要把整份实验设计或报告的每处质量改进都设为硬指标。区分“明确要求交付报告及其必需内容”与“报告论述质量、设计细节的可改进之处”：前者按任务定义必要条件，后者可部分得分。明确要求交付的文件、内容及指定指标不能因“已有大部分工作”而被放宽；任务未要求的内容不得新设为必要项。instructions.md 应说明上述判定方式，并与逐项条件一致。最终复查须检查每层标注有原文依据、无遗漏、互不矛盾，不能把必要条件未满足降为非阻断缺陷。

## 应用：关键结论核验 workflow

按以下顺序执行，并在 scratch/investigation.md 中保留逐项初核、关键复核及最终判定依据：
1. 读原任务和固定 rubric，列出每个 rubric 及子项的必要性、pass_condition 和 veto_condition。对没有必要性标注的旧冻结包，依据原任务识别核心要求并记录依据，不改写冻结标准。
2. 对照真实回答、交付物、初末状态和必要调用结果逐项初核，记录“满足、未满足、无法可靠核实”及证据定位。核查明确要求的实际内容和指标，不能只凭文件存在、工具成功或候选声称完成。区分原始材料、候选成果与验证器自己补做的计算。
3. 对决定整体 pass/fail 的关键事实、数值、推导及必要项结论，至少进行初核和复核两次核验。复核须回到原始证据，重新确认来源身份/工程分支、参数、单位、符号、计算口径、适用条件及结论支持范围；可行时采用另一条证据或独立重算。不能只复读第一次理由，也不能只重复同一个工具返回来声称已独立验证。记录复核方法、结果、发现的矛盾及处理依据；证据冲突须查明，不能挑选支持通过的一侧。
4. 检查决定性结论的理由是否实质正确：谨慎的建议或保守的最终决策不能弥补任务所要求的核心事实、推导或交付错误。接受任务允许的不同合法方案，不额外要求重复解释或固定执行路线。
5. 提交前逐层对照必要项结果、评分理由和整体 outcome。任何必要 rubric 或必要子项已证实未满足，整体必须 fail，summary 指出决定性未满足项；不能用父项高分、平均分、已完成大部分或其他正确结论补偿。扣分本身不自动触发否决，应按明确的 pass_condition 和 veto_condition 判断。必要项均满足仍须核实其他核心实质错误，不能自动 pass。
6. 区分未完成与调查故障：已证实缺失或错误是有效失败判断；影响最终判定的关键事实因调查故障最终无法可靠核实，则返回 verification_error，不伪装成候选未完成或通过。

事实核验、必要性适用和最终 outcome 均由主 Codex 判断；宿主只沿用现有结果校验及加权汇总，不执行额外否决逻辑。以上流程约束同样适用于任务专属 instructions；不得把明确的必要条件失败按“非阻断性局部缺陷”放行。

## 最终输出

最终必须输出 {"task_id":"与 request 一致","outcome":"pass 或 fail","summary":"决定性依据","rubrics":[{"rubric_id":"R1","score":1,"reason":"依据固定标准的理由","evidence":[{"path":"evidence/actual/answer.txt","locator":"行或记录","finding":"观察事实"}]}]}。
task_id、outcome、summary 和 rubrics 都是必需字段；不要使用其他方法的仅 rubrics 输出格式。证据必须是调查目录下 evidence/ 或 scratch/ 中实际存在文件或目录的相对路径；证明缺失时保存目录清单或引用已搜索的目录。
每项恰好一次；binary 为整数 0/1，ordinal_5 为整数 0..5。权重由宿主汇总。可修正自己的调查脚本，不改候选产物和标准；无法可靠继续时输出 {"verification_error":"原因"}，由宿主整任务回退。

主 Codex 根据原任务和核实事实给出整体 outcome，并用 summary 解释：必要项未满足、核心未完成或实质错误为 fail；不违反必要条件且不影响任务完成的局部缺陷可为 pass。不设总分门槛、不改变固定 rubric 分数；总分由宿主汇总。最终 JSON 沿用现有字段，逐层必要项状态及复核过程写在调查记录中，相关 reason、summary 和 evidence 引用决定性事实。
