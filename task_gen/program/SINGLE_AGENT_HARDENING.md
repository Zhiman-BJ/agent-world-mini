# 单 Agent 任务增难与参考解

状态：规则 v9（参考列表仅业务 MCP），默认只准备输入；显式执行时使用已确认的增难原则。历史结果按各自版本留存。
入口：`task_gen/program/single_agent_hardening.py`。

## 1. 最终需求

在已有任务与相同工具、数据、初始环境的基础上，改出更有挑战、真实且可解的新任务。
同一个作者 Agent 同时完成改题、实际解题和参考调用列表，并利用快速验证反馈继续修正。
最后使用 Kimi Code、冻结推理参数和独立 GPT 会话求解新题，保存完整结果供对照检查。

交付包括：中文新题、现实需求说明、完整参考答案、顺序工具列表、参数与答案来源、成功验证 ID。

## 2. 必读材料

宿主代码把以下文件放进作者工作区旁的专用只读目录 `../.task-authoring/`：

| 文件 | 用途 |
| --- | --- |
| `original_task.json` | 原题、原参考答案、原调用数，确定真实用户需求 |
| `original_calls.json` | 原参考工具名和参数，理解原有工作与调用链 |
| `public_tools.json` | 公开工具说明、输入和输出 Schema |
| `protocol.json` | 实际上下文、读取、调用预算和推理参数 |
| `workspace_files.json` | 公开数据文件目录、scope 与挂载说明 |

作者先读上述材料，再按任务对象阅读相关业务数据和规则文件，通过公开工具探索实际能力。
材料目录与业务文件区域隔离，仅作者文件读取入口可访问；独立求解者使用干净初态和新题。
`Read/Grep/Glob` 可用于作者阅读材料、查找公开参数，保留在作者探索轨迹中，不进入参考解调用列表。

## 3. 增难方法与必要规则

作者先分析原题哪些对象、工具、参数或步骤已经给定，以及哪些查询直接给出答案。
结合已有能力扩展真实用户目标，让求解者自己选择和组织工具，结合不同工具的实际返回作出决定，
由决定影响后续处理对象、参数或行动。用最短合理解法核对新增工作是否对新成果必需。
具体改法由场景决定，新增工作应改变交付结果，而不是只增加报告内容。
实际完成参考解后，在 `real_need` 中说明原成果、新成果、现实用途、原解法为何不足，
以及新增的必要判断与操作；这段作者依据不作为独立求解者的解题提示。

必要规则单列：

- 需求真实且可解，允许改写原目标、范围和交付。
- 题文只说明业务目标、对象范围、必要判据和成果标准，工具选择、查询顺序、中间参数与回退路线放在参考解。
- 已知输入路径可以公开，探索得到的候选、证据位置、中间标识和配置组合保留在参考解；来源引用探索结果，验收条件不改写成逐步操作说明。
- 工作形态服从具体业务，主成果可直接使用；不同题不统一套用全面复核、证据对账和交接报告。
- 使用已有工具和数据，参数与结论有公开依据，区分事实、假设和待实施事项。
- 参考解调用列表只包含公开业务 MCP 工具，查得参数直接填入对应接口；文件查看不计入参考调用数，新旧调用数都只统计业务 MCP。
- 文件或状态交付以验证中的实际状态为依据；只返回内容的能力对应内容交付，实际写入能力才对应文件交付。
- 专业计算使用现有领域工具，模型负责判断、结果传递、筛选和简单四则运算。
- 原参考少于 `18` 次时增加必要调用；达到 `18` 次时保留实质难度，调用数按需求安排。

这些业务原则延续 `HARDENING_PRINCIPLES.md`；其中历史多审核 Agent、参考程序和独立链审核
流程由本文替代。必要性和依赖由作者说明，代码核对可验证的来源与执行证据。
v7 保留简短增难方法，将重点移到理解目标、跨工具信息结合和后续行动选择，取消固定的放行/回退双依赖结构。
独立重复查询或增加题文长度不代表增难；探索出的中间信息不能通过写进题文绕开来源核验。
参考解改为绑定快速验证的实际列表与结果，取消手填会话索引；工具接口、调用门槛与计算边界不变。
失败留证及版本、协议分开统计的要求不变。

## 4. 谁做什么

1. **宿主代码准备输入**：选择已有任务，冻结任务、工具、初态和协议的指纹，写作者材料。
2. **一个作者 Agent 改题并解题**：在一个 Kimi Code + GPT 会话中读材料、探索、改题、实测。
   一次会话可以包含多次模型请求和验证修正，作者会话数量仍为一个。
3. **作者调用快速验证函数**：把选定调用列表传给 `validate_solution_calls`，看结果后继续修正。
4. **宿主代码检查最终提交**：核对真实调用、全部参数的公开来源、答案证据，以及成功验证记录。
5. **宿主代码直接重放**：从冻结初态调用已有业务 MCP 接口，检查结果一致性，不重新启动完整 Kimi 会话。
6. **独立 GPT 求解**：在另一个干净 Kimi Code 会话中，使用相同推理配置，仅接收新题和公开环境。

作者会话与独立求解会话各一个。前五步中的代码检查和重放不额外调用审核模型。

## 5. 快速验证接口

实现：`task_gen/program/solution_validation.py`。
作者通过 MCP 支持工具 `validate_solution_calls` 调用；业务工具接口保持原样。

输入示意：

```json
{"calls":[{"tool":"公开业务工具短名","arguments":{"id":"实际参数"}}]}
```

每次验证从作者会话开始时的干净工作区与记录库副本开始，顺序执行整个列表。
业务调用复用正式 MCP 的 `call_environment_tool`，返回真实业务结果；状态修改只发生在验证副本。
列表只接受业务 MCP 工具，作者的文件查看不传入此接口；原来的文件工具简化实现已移除。
验证直接调用共享业务执行函数，不额外启动 Kimi CLI 或模型会话；独立副本用于避免作者探索状态污染参考解。

返回包括：

```json
{
  "validation_id":"本次验证ID",
  "execution_passed":true,
  "semantic_correctness_proved":false,
  "call_count":2,
  "failed_call":null,
  "calls":["每步的工具名、实际参数、结果和错误"],
  "state":{"changed":true,"changed_files":["发生变化的文件"]}
}
```

发生失败时停在该步，返回位置与错误；作者据此修改并再次提交完整列表，最多 `3` 次。
最终提交引用成功的 `validation_id`，宿主核对其输入列表与最终列表完全一致。
最终验证额外传入 `proposal`，即完整新题和参考解（可省略 `validation_id`）。验证器返回
`source_check_passed` 和 `source_check_errors`，作者可在同一会话修正来源并再次验证。
宿主同时核对最终提交与经过来源检查的 `proposal` 一致，避免验证后改题或改答案。
验证请求计入作者会话调用预算，内部重放的调用另行留证；最终参考调用数只统计提交列表。
作者可以继续探索和处理工具失败，独立求解仍沿用原协议的环境错误策略。

## 6. 参考解格式

完整格式与来源示例在 `single_agent_hardening.py` 的 `AUTHOR_PROMPT` 中。
`solution_calls` 每项包含 `tool`、`arguments`、`argument_sources`、`purpose`。
`tool` 只使用公开业务 MCP 短名。作者仍可读取必读材料、查找参数，文件调用不进入参考列表。

`validation_id` 与列表序号唯一绑定真实验证执行，宿主保留并核对完整请求及每步结果。
来源中的 `call` 是最终参考列表的前序序号，JSON Pointer 指向该步验证记录的 `result`。
可引用题文、公开 Schema、协议常量、前序真实返回、基础四则运算及新建输出标识。
从公开文件查得的参数可用 `{"kind":"file","path":"公开工作区相对路径","quote":"实际原文"}` 引用；
数值引用可增加 `"as":"json"`，仅引用已存在的公开文件路径时省略 `quote`。
宿主从冻结初态的公开文件核对引用，不依赖作者修改后的文件或私有记录库，也不要求把文件读取动作加入参考列表。
`schema_choice` 仅允许公开 Schema 的枚举、布尔或默认值，不能用它凭空引入业务对象。
同源数组或对象允许整体引用，例如 `/ids` 引用前序返回的整个数组；整体值必须完全匹配，
每个参数叶子恰好被覆盖一次，缺失、重叠、额外字段和未来来源仍然拒绝。这样减少重复填写，
不改变来源的可见性、时序或数值要求。
参数来源按数值比较整数和浮点数，例如 `100000000` 与 `100000000.0` 相等；不设置近似容差，
布尔值和数字字符串仍与数值区分。题文中带单位的频率可通过 `as: frequency_hz` 明确换算到Hz。

v8 将纯来源核验独立到 `proposal_sources.py`，领域环境不需要加载编排依赖。
整体 `schema_choice` 数组与逐项选择公开枚举等价，仍检查长度、唯一性及每个元素的合法来源。
结果指针默认保留原有JSON类型；`quote` 必须是实际连续原文，`as: json` 只解析合法JSON文本。
一次返回所有可定位的参数和答案来源错误，三次验证上限与业务正确性要求不变。

探索与验证工具本身保存在作者轨迹中；最终参考列表只保留完成新题所需的实测调用。
参数来源与业务合理性分开记录，作者自查与代码可证明的执行事实也分开记录。

## 7. 协议与结果

当前冻结兼容配置：GPT / Responses / `high`，上下文 `262144` token，工具总预算 `65` 次，
Read 默认 `80000`、最大 `128000` 个 UTF-16 字符单位，压缩触发比例 `0.8`，
模型单次输出上限 `131072` token。网关请求头显式记录在运行报告中。

`execution_passed` 代表调用列表可执行，`parameter_sources_match` 代表参数与声明来源匹配。
正式重放结果一致和独立 GPT 完成回答分别留证；业务答案是否正确仍需对照验收。
当前完成状态为 `gpt_completed_pending_answer_review`，`correctness_verified=false`、
`release_ready=false`，避免把执行成功直接报告为准确率。

## 8. 启动与留证

`python -m task_gen.program.single_agent_hardening` 使用 `--input-root`、`--case`、`--protocol`、
`--output-root`。默认准备输入，确认后显式增加 `--execute`。API key 从指定环境变量读取。
历史运行目录、任务与报告保持原样，新流程使用新输出目录。
MCP 列表规则只用于后续新生成的任务，不修改已冻结批次的提示词、工具列表或判定记录，也不自动重启任务。

关键文件：`author_prompt.txt`、`author_materials.json`、`proposal.json`、`source_check.json`、
`reference_tool_calls.json`、`result.json`；每次快速验证保存在作者运行的
`raw/solution_validations.jsonl`，正式重放及独立 GPT 的答案和轨迹单独保存。

固定20题盲测的目标为 GPT 至少18题通过、Qwen至多8题通过。来源、任务、协议和版本先冻结，
生成拒绝、参考验收失败、模型内容失败和基础设施问题分别保留；不能通过换题或改判达标。

批量作者生成、GPT盲解、Qwen盲解和Verifier的默认并发上限均为 `20`；待处理题数少于20时，
实际并发以待处理题数为限。配置上限与实际运行会话数分别报告。

首批20题全部获得有效的GPT/Qwen配对判定后，如果未达目标、GPT至少17题通过且Qwen不超过9题通过，
允许固定补测10道新题。补测前冻结题目、版本和协议，保留首批全部结果，按合并30题统计：
GPT至少26题通过、Qwen至多12题通过。不能反复补测到达标，也不能混入不同版本或挑选有利结果。
有基础设施失败时先报告缺测，不以缩小分母后的通过率宣告达标。

Responses传输只对产生任何模型输出之前的临时断流做有界重试，记录每次请求和错误；
开始输出或涉及上游执行工具时不自动重放。上下文、鉴权及输入错误不作为临时故障重试。
MCP预检只初始化与枚举工具，不复制验证环境；首次业务调用前保存干净初态，验证副本仍独立。
