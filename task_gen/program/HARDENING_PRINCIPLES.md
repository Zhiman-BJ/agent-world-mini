# 任务增难原则（冻结清单）

本文保留旧版本的原则基线和验收语义，不作为新版启动说明。
当前流程见 [SINGLE_AGENT_HARDENING.md](SINGLE_AGENT_HARDENING.md)，其中明确替代的
多 Agent 审核、参考程序和独立链审核要求不再执行；未替代的业务原则继续保留。

这份清单是直接改写已有任务的共同约束。新的作者提示词、审核提示词和批次报告必须与它一致；
如果某个旧版本提示词与本清单冲突，以本清单和该版本已冻结的运行记录为准。修改原则时必须新建版本和输出目录，不能追认旧结果。

## 1. 目标与范围

- 增难对象是已经存在的任务变体，不重新运行原 Program 的任务生成 Step 1/2，不重新抽样，不改变原题的冻结初始状态。
- 变体必须服务于原题相关的现实用户、业务对象和决策，不得换成无关领域、纯学术谜题或只为降低模型通过率设计的题。
- 可以重写主目标、对象范围、约束、交付形式、工具顺序和调用链；不要求逐项保留原题旧交付，但必须说明删改理由。
- 新任务必须由已有公开工具、公开数据和冻结环境真实支持；不能新增工具、伪造返回、私读数据库、引用作者私有会话或隐藏答案。
- 参考解调用列表只包含公开业务 MCP 工具；作者可用 `Read/Grep/Glob` 查找公开参数后填入对应业务接口，文件查看留在探索轨迹，不计入参考列表和新旧调用数。验证复用现有业务接口，不为参考列表重启完整 Kimi 会话。
- 任务可以是只读环境中的具体选择、配置、分析或决策设计；不得把工具不支持的实验、测量、部署、下单、预约或写状态声称为已完成。

## 2. 真实工作成果

- 主成果必须是用户可以直接使用的结果：例如已确定的选择、参数、排程、设计、比较、处置结论或有边界的方案。
- 不能以旧答案复述、证据清单、缺口清单、资格/接收审核、泛泛建议或“未来需要做什么”为主要成果。
- 复核、对象关联、条件分支、证据对账、异常恢复和结果回读都是可选的业务机制，只有在真实需求需要时才加入；不要求每题套模板。
- 难度来自完成主成果所必需的真实选择、约束、分支、证据范围、单位/版本差异或结果验证，不来自题文变长、表格变多或报告格式变复杂。
- 题文描述业务目标、范围、必要判据和成果验收；工具选择、查询顺序、中间参数与回退路线属于参考解。已知输入路径可以公开，通过工具才能发现的对象、证据和选路由求解者自行发现。
- 区分业务规则与操作教程：例如交付物的精度和合法范围需要明确，先查哪个工具、失败后读哪个文件不写成用户指令。编号本身不违规，编号内的逐步解法才是检查对象。
- 模板化按实际工作机制识别：不同领域反复扩成“全面复核、证据对账、交接报告”仍属同质化；术语替换、长表格和增加子项不等于新的决策负担。
- 对现实实验或部署只能交付可执行设计和明确前置条件；答案必须区分已观察事实、工具计算结果、作者推断和未来待实施事项。

## 3. 调用链与增难门槛

- 原参考调用记录是冻结比较基线，可能包含探索，不声称它是最短解；新旧必要调用和依赖链必须由独立审核者按实际结果重新识别。
- 只有最终参考程序从冻结初态实际执行的工具调用计入调用数；作者探测、失败重试、未使用结果、静态复杂度和 Python 循环不计入。
- 原参考实际调用数小于 `18` 时，新版实际调用数、独立认定的必要调用数和最长业务结果依赖链都必须严格增加。
- 原参考实际调用数大于或等于 `18` 时，不强制增加上述数量，但仍必须有实质业务增难；允许删除原有探索或冗余调用，不得借豁免简化任务。
- 每条依赖边必须由前序真实返回的对象标识、版本、单位、范围、状态、参数或选路结果决定后续调用；仅按时间顺序、相同硬编码值或并列查询不算依赖。
- 禁止重复查询、把一个批量查询人为拆开、重复导出同一内容、附加哈希/长表格、失败重试凑数或用无关复核凑链。
- 单题最终工具调用上限保持 `65`；达到上限不能替代可解性和业务必要性证明。

## 4. 程序与计算边界

- 参考程序只能用 `call_tool(name, arguments)` 获取业务数据，并按真实 `success` envelope 读取返回值；不能猜字段后写死答案。
- Python 只负责编排：赋值、容器处理、遍历已有记录、条件分支、结果传递和简单比较/加减乘除。
- 禁止 NumPy、SciPy、SymPy 等计算库，禁止自行实现优化、拟合、数值求解、复杂边界证明或组合穷举；不能用普通循环绕过限制。
- 专业计算只能由环境中已有公开领域工具完成，工具返回必须实际进入参考答案；计算工具的内部实现不算作者私有算法。
- 最终答案必须由本次真实工具返回生成，不能复制原答案、写入隐藏常量或依赖探测阶段的私有状态。

## 5. 证据、可解性与质量门禁

- 题文必须公开所有决定答案所需的对象范围、单位、判据、适用范围、同分处理和必要限制；不能把关键规则藏在参考程序中。
- 每个新增要求都要能在公开环境中找到真实证据，且参考程序实际执行了覆盖该要求的调用；工具成功不等于业务结论自动成立。
- 文件与状态交付以干净初态验证的实际状态为依据：工具返回一段JSON内容不等于已生成JSON文件；题文要求持久文件时必须有已有工具实际写入的证据。
- 参考答案必须完整交付主成果，正确处理空结果、缺失字段、异常状态、冲突证据和工具能力边界；不能用未来工作填补当前缺失结果。
- 独立审核必须同时检查业务相关性、真实增难、公开可解性、无人工膨胀、程序计算边界、答案完整性和依赖证据。
- 参考执行成功、审核通过、MCP 重放通过、独立 verifier 通过是不同门槛，任何一项缺失都不能标记为可用变体。
- 审核失败的原题保留并记录具体原因，不用其他题替换，不把失败候选送入训练或模型准确率分母。

## 6. 上下文与评测协议

- 正式长上下文协议使用 `256K` token 上限；读取工具默认输出 `80K` 字符，单次上限 `128K` 字符。
- 读取结果拼接后仍需按剩余上下文预算触发压缩；压缩不得丢失工具调用、思维链中对后续决策必要的事实、对象标识、单位和错误状态。
- 压缩输出预算、工具调用上限、并发和推理强度必须写入运行配置并冻结；不同协议的历史结果不能直接混合比较。
- 上下文耗尽、工具预算耗尽、基础设施错误、参考验收失败和模型内容失败必须分别统计，不能互相替代。

## 7. 最终目标与测量顺序

- 最终集合目标是 `20` 道经过参考执行、独立审核、MCP 重放和 verifier 验收的任务；先保证任务质量和覆盖，再进行模型盲测。
- GPT 盲测目标是通过率严格超过 `85%`；Qwen 基模不超过 `40%`。固定20题对应 GPT 至少18题、Qwen至多8题通过，两者在同一任务版本、同一上下文/工具预算下测量，模型原有推理强度差异显式记录。
- GPT 和 Qwen 的准确率不能通过改判、剔除失败题、把未完成题移出分母或按模型失败记录反向改题获得。
- 正式报告必须同时给出任务覆盖、参考验收通过数、GPT/Qwen 已完成数、预算/上下文终止数、基础设施错误数和准确率分母。
- 20 题达到完整验收后，先做 GPT 配对盲测确认可解性，再在 16 张 H100 的正式部署协议上跑 Qwen 基模；不能用五题试点或部分覆盖率宣称最终目标达成。

## 8. 版本执行规则

- 原 v5、v6、v7、v8 运行记录保持不可变；本次 `18` 次门槛使用新版本和新输出目录。
- 新版本必须冻结：原则文件哈希、作者 prompt 哈希、审核 prompt 哈希、输入任务哈希、工具/环境哈希和评测协议。
- 任何作者超时、审核拒绝或参考验收失败都保留完整草稿、调用索引、错误和重试记录；最多按批次配置执行有限重试，不能无限重跑直到通过。
- 按批次版本迭代通用生成策略，模型评测前冻结20个来源身份与题文；失败题保留，不替换、不挑选单模型失败题形成集合。若未达目标，完整报告该版本，再作通用修订并重新测量。
