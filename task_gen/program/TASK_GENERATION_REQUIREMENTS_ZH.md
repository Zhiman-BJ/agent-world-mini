# Program Form 任务生成要求

本文档固化当前 task_gen/program 管线的目标、Agent 行为和发布标准。后续修改 Prompt、Schema、质检或重试逻辑时，应以这些要求为准，避免为了单个环境临时增加会导致任务模板化的规则。

## 一、管线范围

当前只负责 Step 0—2：

1. **Step 0：加载环境**：按 ToolGen/Harness 交付契约解析绑定，准备公开环境、初始状态摘要、工具契约和受限资源。
2. **Step 1：调研现实任务**：结合真实行业资料与当前环境实际能力，找出环境能够完整支撑的现实工作。不得预设固定任务类型，也不得把工具清单改写成任务清单。
3. **Step 2：生成任务与正确 Solution**：每次只生成一条任务；同一个 Agent 负责设计任务、编写 Solution、调用统一质检、读取反馈并修改同一个候选，直到发布或达到修复上限。

Rubric、外部任务评测和 Docker/系统依赖修复不属于当前阶段。

## 二、模型与运行方式

- 默认模型：gpt-6-sol。
- 推理强度：high。
- 一次运行只生成一条任务；批量生成通过重复完整流程实现，不在单次运行中生成多个候选再择优。
- Agent 应能查看公开工具说明和允许查看的工具代码，并在隔离环境中试用工具确认能力。
- 生产运行默认给单个 Agent 3600 秒总预算，给一段完整 Solution 1000 秒总执行预算；Harness 中单个工具仍保留独立的 300 秒上限。科学工具需要反复启动绑定的 Python Profile 时，15 次以上有效调用不能沿用只适合短测试的 180–300 秒整段预算。
- 单条任务默认最多进行 6 轮定向修复（初次质检之外），并始终保留明确硬上限，防止无限重试。结构、执行、语义、重放等不同阶段可能依次暴露问题，不能因前几轮修复有效就过早终止。

## 三、输入上下文

Agent 不应收到一个要求其直接理解的巨大环境 Schema。输入应由以下几部分组成：

- 与当前环境对应的公开业务或科研背景；
- 当前任务可能使用的记录集合、文件区域和关系；
- 工具名称、用途、输入输出契约和可用资源边界；
- 必要的初始状态摘要；
- Step 1 产出的现实任务调研；
- 已发布任务的大体描述，用于避免同一环境反复生成近似任务。

具体任务正文应自然说明完成工作所需的材料、对象、目标和约束，但不应向执行 Agent 暴露完整环境内部结构、隐藏答案或实现步骤。

## 四、现实性要求

- 任务应是现实业务、工程或科研流程中的具体工作，而不是为了调用工具而拼接的题目。
- 默认目标不应是“审计、复核、核查、检查”。只有该环境的真实工作本身就是验收或质量控制时，才可生成此类任务。
- 任务可以包含研究分析、设计选择、参数迭代、方案比较、结果驱动决策、产物生成与回读验证等自然过程，但不得把这些形式写成固定模板。
- Step 1 应调研多个环境可支撑的真实工作，Step 2 自主选择最合适且有难度的任务，不提供固定任务类型枚举。
- 任务背景、材料、约束和最终交付应连贯自然，不要求使用固定段落标题或固定句式。

## 五、难度与工具使用

- 任务难度来自真实工作中的信息依赖、推理、计算、选择、迭代和结果验证，而不是人为增加无意义步骤。
- 当前批量生产目标为每条已发布任务至少 15 次有效工具调用。
- 不强制某一种工作流形态，也不要求所有调用都形成单一串行依赖；允许多来源证据、多对象计算、独立方法交叉验证、结果筛选、迭代优化、写入后验证和串行依赖自然组合。
- 不得通过重复无意义调用、把一次操作机械拆分或调用与任务无关的工具来凑次数。
- 所有调用必须直接服务于同一个核心业务结果。不得为了增加长度附加环境依赖核查、运行条件盘点、资源清单或其他与核心结果没有直接因果关系的工作；只有现实交付明确需要时才可包含。
- 工具数量很多并不自动意味着任务应调用全部工具；调用必须共同服务于一个现实目标。

## 六、Solution 规则

- Solution 只使用管线允许的受限 Python 子集和工具调用，不应使用任意文件系统、网络、子进程、反射、动态执行或其他未授权 Python 能力。
- 允许用变量、容器、索引、循环、条件分支和必要的基础计算组织工具结果。
- 每次工具调用的每个业务参数必须来自任务正文、前序工具调用返回值，或对这些值进行任务明确允许的确定性计算。
- 禁止凭空加入默认查询、排序、分页、阈值、路径、对象 ID 或文件名，例如无来源的 query 空值、sort_order、limit 或 offset。
- 后续对象 ID、文件路径和选择参数应尽可能来自前序工具结果。
- 把工具输出传给后续工具前，必须核对字段、数据形状、唯一性、排序和取值约束；上下游不兼容时应调整处理方法或任务设计，不能强行拼接调用。
- 工具返回失败时必须保留真实错误信息；不得用裸 assert、统一异常文案或伪造结果掩盖失败。
- final_answer 必须完全由任务输入和真实工具结果构造，输出为完整的用户可读文本，且最后一条语句为 final_answer 赋值。

涉及文件资源时，任务正文必须自然写明文件区域和区域内相对路径。一次声明多个精确文件时，每个文件都必须独立写出完整相对路径，不能在第一个文件后仅写文件名或使用“同目录下”等省略表达。

## 七、生成与修复闭环

Step 2 的同一个 Agent 应执行以下闭环：

1. 阅读环境、调研结果和历史任务摘要。
2. 设计一条现实且较难的任务。
3. 编写可执行 Solution 和输出 Schema。
4. 调用统一候选质检。
5. 根据返回的具体错误修改当前候选，而不是重新生成无关任务。
6. 重复质检与修改，直到达到发布标准或修复轮数上限。

质检反馈必须面向修复，至少指出错误位置、失败阶段、真实工具错误、参数来源问题或任务与答案不一致之处。对于确定的基础设施不可用工具，应标记为终止型错误，要求 Agent 更换可执行任务路径，而不是重复调用或掩盖错误。

统一质检应复用同一次真实执行产生的 trace、答案与状态证据：先完成候选结构、执行和资源契约检查，再做 Semantic Review；只有语义审查通过后才执行干净重放。不得在同一轮质检中为了预检查和语义审查重复执行相同 Solution，也不得在已经明确存在语义问题时提前消耗完整重放成本。

如果生成 Agent 超时、异常退出或已经无法继续读取反馈，质检服务必须在有界时间内停止并释放并发槽，不能因后台质检线程仍在运行而永久阻塞整批任务。此类退出应保留最后一次具体反馈，允许后续使用同一候选进行定向重跑。

独立 Semantic Review 如果返回缺字段、不可读 issues、空拒绝或其他不符合审阅契约的结果，质检层应携带格式错误自动重试审阅；这类审阅器输出故障不得消耗候选任务的修复轮次。只有审阅结果结构有效并给出具体业务或参数问题后，才把问题反馈给生成 Agent。

## 八、发布标准

只有同时满足以下条件，任务才能写入 tasks.json：

- 任务正文、声明的记录或文件资源和实际 Solution 一致；
- 有效工具调用次数达到当前运行阈值；
- 所有工具参数均可追溯；
- Solution 可在干净环境中执行；
- 最终答案完整覆盖 task_text 的业务要求；
- 最终答案的业务含义与任务要求一致；
- Semantic Review 通过；
- 多次干净重放结果一致；
- 发布内容与 Ground Truth 一致。

任务若因 Docker、动态库或系统包缺失失败，当前阶段不修复基础设施；应保留真实错误并避免把该工具路径计为生成管线逻辑缺陷。

## 九、质量与成功率验收

管线优化完成必须同时满足：

- 在不少于 10 个具有代表性的不同环境上运行完整 Step 0—2；
- 至少 70% 的环境成功发布任务；当前“达到 70% 以上”的验收目标按 10 个环境计应达到 8/10 或更高；
- 已发布任务满足至少 15 次有效工具调用；
- 抽查任务具有现实性、自然语言流畅、不是批量模板替换、Solution 正确；
- 失败样本已按 Step 1、候选契约、执行、调用次数、参数溯源、Semantic Review、重放和 Schema 等阶段分类；
- 对占比最高的非 Docker 根因完成针对性修复和回归测试。

在上述证据全部具备前，不应宣称管线已经达到目标。

固定验收环境见 `benchmark_non_docker_10.json`。除非环境交付本身发生变化，不应根据某次生成结果替换其中的环境；若某个环境出现 Docker、动态库或系统依赖阻塞，应保留原始分类和证据，并另补一个满足相同选择标准的环境用于非基础设施成功率分母。
