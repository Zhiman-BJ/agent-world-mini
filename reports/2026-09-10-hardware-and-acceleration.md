# 硬件检查与 Qwen 加速结果

检查时间：2026-09-10 11:42–11:44，运行状态是瞬时快照。

## 加速已经完成的部分

服务仍只使用 GPU 0、1，BF16、128K 上下文、medium 推理、最多同时处理两个请求。
移除了 enforce-eager，torch.compile 和 CUDA Graph 均成功启用。
移除了 disable-custom-all-reduce 后，vLLM 检测 P2P 不可用并自动回退 PYNCCL，
因此通信优化没有获得新的后端。服务正常运行，原启动参数及全部旧日志保留。

同一个真实 ReAct 初始请求，固定 seed=42、temperature=1.0、输出128 token，
ignore_eos 仅用于速度测试，不用于真实任务。每个配置3次请求，后两次作为预热后观察：

| 配置 | 首次请求秒 | 后两次请求秒 | 后两次吞吐 token/s |
|---|---:|---|---|
| 原 eager | 10.74 | 9.91 / 9.81 | 12.91 / 13.05 |
| 编译与 CUDA Graph | 12.54 | 4.31 / 4.30 | 29.70 / 29.76 |
| 再允许自动通信优化 | 12.49 | 4.32 / 4.30 | 29.61 / 29.77 |

预热后的请求速度约为原来的2.3倍。首次请求包含长输入预填充，原服务已有缓存，
不能用第一列作公平冷启动比较。其他用户负载未受控制；只有短测，不能据此声称
完整 ReAct 任务快2.3倍。最终正常 JSON 请求也通过：10.05秒返回有效论文搜索 action。
原基线三次短测在用户要求不再测基线前已结束，此后未追加基线。

## 当前负载和部署判断

短采样CPU空闲约65%–72%、IO等待0%，可用内存充足。负载平均约48，但机器有
124个在线逻辑CPU，不能仅凭load值断言CPU满载。其他GPU用户正在运行，不做争抢资源的全机压测。

就当前证据而言，主机内存容量不是这个Qwen服务的限制。GPU计算/显存访问、
跨卡通信与每轮生成长度仍决定速度；没有内核级剖析，不能给各部分占比或断言唯一瓶颈。
默认BF16的27.78B参数仅权重约51.7GiB，超过单卡可见显存，当前双卡部署有必要。
以后若有空闲卡，多个双卡实例是值得测的吞吐方案，更多卡合并一个实例不保证加速。

下一项获授权计划是同一实例多任务并发；目前只完成这两个启动参数优化，没有新建verifier，
没有改变任务prompt，也没有降低模型精度或推理档位。

另一个可独立测试的小项：vLLM日志警告OMP_NUM_THREADS=8可能造成CPU争用。
可比较默认1线程和当前8线程，必要时再测试CPU/NUMA绑定；此次没有叠加修改，避免混淆收益。

未测项目：磁盘真实吞吐/IOPS、CPU/内存带宽、PCIe实际带宽、网络吞吐、长时间满载稳定性。
这些结论需要额外压测，不能由硬件名称推算成实测结果。
